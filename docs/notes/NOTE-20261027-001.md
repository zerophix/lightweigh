# UI 已铺开、DDD 层未接入：缺口清单与接入计划

> **日期:** 2026-10-27
> **状态:** 规划文档（供人审与后续任务建单，未定稿为 DEC）
> **方法论:** 只读检查 app 层 174 个文件 + application/domain 能力清单 + AppContainer 装配表，逐屏对照「UI 壳」与「DDD 数据流」是否接通。
> **证据口径:** 所有数据来自本仓实测命令，`grep` 与 `cat` 取证，路径见文末附录 A。

---

## 1. 问题一句话

**UI 层铺开了大量呈现式组件（约 20 个屏），但支撑这些屏的 DDD 业务逻辑（application service + domain 端口 + ViewModel 数据流）大多没有接入**——多数屏用 `remember { mutableStateOf(...) }` 持本地演示状态，副作用回调是空实现，代码注释自己写着「本轮只完成状态推进」「真实提交在调用方」「不假装已接数据层」。

这与`docs/ai/inbox/20261024-053049`里记录的「**接入波**：19 个已交付呈现式屏未接入导航/ViewModel/数据层 → 功能不可达（最高优先）」完全吻合——那批屏的导航已补（`WiringEntries.kt`），但**数据层接入仍未完成**。

`app/src/main/kotlin/com/xcwk/scalehub/App.kt` 的 `AppContainer` 已暴露以下端口与用例，**全部有真实实现**：

## 3. 缺失能力清单（DDD 层需要补的）

对照 A 档屏幕，DDD 层**已具备**的能力多数够用，真正**缺失/需扩展**的集中在：

| 缺失能力 | 归属层 | 服务哪些屏 | 缺口类型 |
|---------|--------|-----------|---------|
| **设备重命名写用例** | application + domain | DeviceRename | 缺 `rename` 写端口/用例 |
| **成员↔设备绑定写** | application + domain | MemberDeviceLink | 缺绑定关系写模型 |
| **设备固件版本查询/更新** | application + infrastructure | FirmwareManager / DeviceDetailScreen | 缺固件字段 + 更新用例 |
| **反馈/诊断工单落库** | application + infrastructure | FeedbackFlow / HelpCenterFlow | 缺 FeedbackService + 工单表 |
| **隐私授权状态持久化** | application + domain | PrivacyAuthFlow / MemberPermissionDetail | 缺授权模型 + 读/写用例 |
| **数据冲突检测**（对账驱动） | application（SyncService 扩展） | DataConflict | SyncService 已有对账，缺暴露成可订阅冲突状态 |
| **维护模式健康检查** | application + infrastructure | MaintenanceScreen | 可复用 ServiceStatus 探测 |
| **AI 周报生成** | application | AiWeeklySummary | AiService 仅 `ask`，缺周报结构化生成 |

**其余（ActionPlans / AiBoundaries / ResultShare / DataRecovery / ProfileSetup / PermissionFlow / GuideScreen / SdkListScreen）能力已具备**，只需在 Route 建 ViewModel、把演示 `remember` 换成从 AppContainer 注入真实用例。

## 4. 接入计划（分 4 批，依赖先行）

> 排序原则：先接「能力已具备、只需换数据源」的低成本项，再接「需补 DDD 能力」的中成本项，死代码最后裁决。

### Batch 1 — 能力已具备，纯接线（低风险，5 屏）

每屏只做：建 ViewModel → 从 AppContainer 注入已存在用例 → 替换 `remember` 演示状态。

| 屏 | 接线动作 |
|----|---------|
| **DataRecovery** | 接 `RestoreAccountService.execute()` 驱动恢复进度/结果 |
| **ProfileSetup** | 接 `UpdateProfileService` + `guideSeen` 标记 |
| **PermissionFlow** | 接真实权限请求 + `guideSeen` 持久化 |
| **GuideScreen** | 接 `guideSeen` 持久化 + 完成写 `UpdateProfileCommand` |
| **AiBoundaries** | 接 `AiService.ask()` + `AuthPort.isFormalAccount` 推导六态 |

### Batch 2 — 需补 DDD 能力（中风险，5 屏）

| 屏 | 补的能力 | 落点 |
|----|---------|------|
| **DeviceRename** | `DeviceRepository.rename()` 写用例 | domain 端口 + application service + Room 实现 |
| **MemberDeviceLink** | 成员↔设备绑定写模型 | domain 模型 + application service |
| **FirmwareManager** | 固件版本查询/更新 | infrastructure 固件源 + application query/service |
| **FeedbackFlow + HelpCenterFlow** | `FeedbackService` + 工单落库 | application service + Room 工单表（schema v8） |
| **PrivacyAuthFlow** | 授权状态持久化 | domain 授权模型 + application service |

### Batch 3 — 复用既有复杂能力（高风险，4 屏）

| 屏 | 接线动作 |
|----|---------|
| **ActionPlans** | 接 `HabitQuery` + `RecordHabitService`；周计划生成接 `AiService` |
| **ResultShare** | 接 `ReportQuery` 取报告文本 + 真实分享/导出 |
| **DataConflict** | 扩展 `SyncService` 暴露可订阅冲突状态 |
| **MaintenanceScreen + SdkListScreen** | 接 `ServiceStatus` 探测 + SDK 配置外提 |

### Batch 4 — 死代码裁决（4 文件）

| 文件 | 裁决 |
|------|------|
| `AiCards.kt` / `MeasureHelp.kt` | 确认产品是否需要；不需要则删或留作预览 |
| `AccountLifecycle.kt` | 接 Route（若产品要求账号生命周期多屏） |
| `HealthConnectPlatform.kt` | 待真机验收后决定是否实现 |

## 5. 验证口径

每个接入任务完成后走现有闭环：

1. **`./gradlew :app:testDebugUnitTest`** — 新增/修改 ViewModel 的 JVM 单测（含负面测试：演示数据被替换、回调不再空）
2. **`bash scripts/governance/gov-prototype-verify.py T-xxx --strict`** — 接入后原型文案不回归
3. **`bash scripts/governance/gov-validate.sh`** — 文档/注册表一致性（新增测试需登记 `tests/android-test-registry.yaml`）
4. **`bash scripts/governance/gov-local-ci.sh`** — 合入前全量验证
5. **ArchUnit 守卫** — 确认接入不破坏 `app → application → domain` 依赖方向

## 6. 建议

1. **先清 3 项门禁债**（Git hooks 未装、`.cache/dev-mode` 白名单、测试注册表 8 未注册 + 5 僵尸）——否则新任务合入会被 pre-commit/local-ci 卡住。
2. **Batch 1 可并行**（每屏新建文件、互不抢文件，符合 `GOV-PTASK` wave 分组）。
3. **本计划如定稿，请逐屏建 `.ai/tasks.json` 任务**（`wf-task-board.sh add`），并给每屏补 `target_files` + `prototype_ref` + AC，走 `gov-task-done` 闭环。
4. **要不要落 DEC**：本计划是否转 DEC 取决于是否要形成「接入波统一口径」决策；若仅作为排期清单，维持 NOTE 即可。
