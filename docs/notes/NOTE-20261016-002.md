# DataRefreshBus 扩展边界

> **来源:** AI-DISCUSSION
> **日期:** 2026-10-16
> **状态:** 活跃
> **相关决策:** DEC-021

---

## 背景

深入核查 `application/DataRefreshBus.kt`（DEC-021 支柱 2「跨屏刷新由数据源信号订阅决定」的实体化），
判断它是否仍是旧库 `UiRefresh.version++` 全局总线的新形态，是否构成后续切片扩展的隐患。

## 现状核查（基于真实代码）

`DataRefreshBus` 是一个 `MutableSharedFlow<Unit>`，无业务载荷，`notifyChanged()` 发射空信号。

- **生产方**：application 层写用例，落库成功后调用。
  - `RecordMeasurementService.save` 后
  - `RecordHealthLogService` 保存后
  - `DeleteMeasurementService` 删除后
- **消费方**：feature 层读 ViewModel，collect 到信号各自 `refresh()` 重查读模型。
  - `MeasureViewModel`、`HistoryViewModel`、`TrendViewModel`
- **无订阅时**：`tryEmit` 丢弃（extraBufferCapacity=1 无 replay），没有活页面就无需刷新。

## 判断：不是旧总线，但在边界内

| 维度 | 旧库 UiRefresh.version++ | DataRefreshBus |
|------|------------------------|----------------|
| 载荷 | 全局版本计数 | 无载荷 Unit |
| 谁来刷 | 页面"自觉"看版本 | 订阅者各自 refresh |
| 无订阅 | 版本仍递增 | tryEmit 丢弃，不空转 |
| 变更粒度 | 无差别 | 无差别（不辨数据源） |
| 可推理性 | 不可（全局计数） | 半可推理（订阅显式，信号无源） |

- **比旧库强**：依赖方向正确（总线在 application，domain 不依赖它）、订阅关系显式（ViewModel
  init 里 collect，非页面自觉）、无订阅不空转。当前 3 个消费方下**不构成实质危害**。
- **仍是无差别广播**：`Unit` 不带"哪个聚合变更"，任何一次写都会触发所有消费方重查，无细粒度过滤。

## 扩展性隐患（切片增长时触发）

1. **无差别广播的平方级重查**：消费方逼近 ~8 个时，每次写操作让所有页面重查一遍，即使与变更无关。
   无效重查询随切片数增长而非线性扩散。
2. **信号无来源标识**：`Unit` 无法表达"哪个聚合变更"，做"只有趋势页刷、历史页不刷"做不到细粒度。
3. **notify 靠人工契约**：每个新写用例都要记得调 `notifyChanged`，漏调消费方静默不刷新，靠自觉。

## 优化方向（未执行，留待触发点）

- **P1 信号带聚合维度**：`SharedFlow<Unit>` → `SharedFlow<DataChange>`（enum：MEASUREMENT /
  HEALTH_LOG / PROFILE），消费方按自己关心的域过滤，切片增长仍保持细粒度。
- **P2 领域事件替代全局单例**：repository/use-case 暴露领域事件流，让"某聚合变更"成为领域一等公民，
  ViewModel 订阅自己关心的聚合，而非"一切变更"。
- **P3 给 notify 加规则守卫**：配 ArchUnit/测试规则强制写用例带 notify，或由 AppContainer 统一装配，
  把 notify 从"用例责任"变成"仓储契约"。

## 结论

`DataRefreshBus` 当前是**可接受边界内的合理折中**，但本质仍是无差别总线。真正的改造触发点是
**切片数量增长**（消费方逼近 ~8 个），届时落地 P1 细分或 P2 领域事件。本文档记录该边界，避免
未来把它误判为已根治，也避免在切片尚少时过早过度设计。
