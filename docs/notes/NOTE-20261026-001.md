## 0. 本文解决什么问题

本文回答四个连在一起的问题：

1. 这个仓库的 AI 开发流，**实际**长什么样（不是文档宣称的样子）；
2. `docs/` 与 Notion 各自承担什么角色，边界在哪里；
3. 把它放到 2026 年的开源生态里，**哪些领先、哪些落后、哪些根本没有**；
4. 如果要做成通用方案，原语应该怎么抽；如果只优化本仓，应该按什么顺序改。

写这篇笔记的直接动机，是分析过程中发现了三个"机制存在但没在跑"的事实：完成证据目录不存在、任务板上没有任何一条可合法开工的任务、蒸馏规则里还写着一条早已退役的强制约束。这三个事实单独看都是小问题，放在一起说明一件事——**这套流程的能力已经超过了它的自检能力**。能力是加法堆出来的，自检却没有同步堆，于是"看起来有"和"实际在跑"之间的差距越来越大。

因此本文的结论不是"再加规则"，而是"先修回路，再补空白层，最后减重"。

## 1. 现状解剖：四平面与六件套

### 1.1 数据快照

先看硬数据，避免被文档叙事带偏。

| 维度 | 实测值 | 取证方式 |
|------|--------|----------|
| 提交历史 | 611 commits，覆盖 10-15 至 10-25；单日峰值 244 | `git log --pretty=%ad --date=short` |
| 代码测试 | 66 个 Kotlin 测试文件、830 处 `@Test` 注解 | `grep -rho '@Test' app/src/test` |
| 流程测试 | 37 个 pytest 文件、325 个用例 | `grep -rh '^def test_' tests` |
| 治理脚本 | 45 个以上（governance 42 + workflow 14 + session 7 + dev 4），合计 16,357 行 | `wc -l scripts/**/*.sh scripts/**/*.py` |
| 校验器 | 14 个 validate 模块 | `ls scripts/governance/modules` |
| 任务板 | 83 条：56 `completed`、15 `done`、12 `pending` | 见 1.3 的发现 |
| 决策日志 | DEC-001 至 DEC-071，共 72 个文件 | `ls docs/ai/decisions` |
| 文档总量 | docs 下 120 篇以上（含索引） | 分目录统计 |
| 原型 | 11 个 HTML 文件，交互版另有 26 个文件、192 屏 | `ls design/prototypes` |
| 门禁跳过日志 | 单日 60 行以上，含 master 分支记录 | `.ai/gov-skips/2026-10-25.log` |
| 最近一次 local-ci 证据 | 2026-10-24，6/6 通过 | `.cache/local-ci-last.json` |

这组数据的形态很清晰：**提交极碎、验证极密、任务极细**。它不是人写大 PR 的节奏，而是 AI 高频小步加机械门禁兜底的节奏。理解这一点，后面所有判断才有意义——用"人写代码"的标准去评价这套流程，会得出完全错误的结论。

### 1.2 四平面结构

把六件套（治理脚本、docs、Notion、tools、tests、SKILL 与 AGENTS.md）摊开，能看到一个清晰的分层结构。这个结构本身是这个仓库最重要的架构事实，也是它与多数开源方案最根本的差别。

```
┌──────────────── ① 指令平面（软，AI 读）────────────────┐
│ AGENTS.md 228 行：索引 + 规则到执行者映射               │
│ .opencode/skills 3 个：dev-flow / docs-manage / prototype-dev │
│ 蒸馏副本：.cursorrules / .clinerules / .opencode/rules.md │
└───────────────────────────┬────────────────────────────┘
                            │ 只调命令，不叙述规则
┌───────────────────────────▼──── ② 执行平面（硬，16357 行）──┐
│ workflow：autopilot / claim / queue / run / parallel        │
│ governance：validate(14 模块) / local-ci(3 车道) / task-done │
│ hooks：pre-commit → pre-push → commit-msg（hooksPath 统一） │
└───────────────────────────┬────────────────────────────┘
                            │ 读写
┌───────────────────────────▼──── ③ 事实平面（真源）─────────┐
│ .ai/tasks.json 83 条（AC / verify_commands / prototype_ref）│
│ docs：DEC 72 篇、lifecycle 6 篇、inbox 32 封、GC 10 篇      │
│ Notion：产品范围与 AC 的权威方（74 个页面）                 │
│ design/prototypes：UI 唯一真源（26 HTML / 192 屏）          │
└───────────────────────────┬────────────────────────────┘
                            │ 被校验、被消费
┌───────────────────────────▼──── ④ 验证平面（1155 个测试）──┐
│ tests/unit 37 文件 325 用例（含负向测试，证明规则真会拦）    │
│ app/src/test 66 文件 830 用例（ArchUnit、黄金向量、schema）  │
│ android-test-registry.yaml + e2e journeys（需真机）         │
│ tools/：new-project.sh + ddd-android 架构描述（几乎未接线）  │
└─────────────────────────────────────────────────────────────┘
```

四平面里，绝大多数开源 AI 开发方案只覆盖①（提示词与技能），部分覆盖①加③（规格与任务），很少同时具备②（机械门禁）与④（可执行验证）。这是本仓的结构性优势，也是它体量失控的原因——四个平面都要人维护。

### 1.3 六件套的真实职责

| 件套 | 真实职责 | 量化 | 薄弱处 |
|------|----------|------|--------|
| 治理脚本 | 把规则变成可执行程序，是唯一能阻断提交的层 | 45 个以上脚本、14 个校验模块、3 个钩子阶段 | 16k 行自研 shell，只服务单仓 |
| docs | 决策记忆、交接记忆、规范、真源声明，并被校验器消费 | 72 篇 DEC、32 封交接信、5 条文档校验规则 | 与 Notion 的镜像仅 2 个文件有声明 |
| Notion | 产品范围与 AC 的权威、非技术角色协作面 | 74 个页面、8 层目录 | 不可机器校验，只有一句软约定 |
| tools | 新项目脚手架（DDD Android 架构描述） | 2 个文件 | 与主线流程几乎无咬合，接近死代码 |
| tests | 门禁的验证层，负向测试证明规则真生效 | 1,155 个测试 | 没有输出质量度量 |
| SKILL 与 AGENTS.md | 把"该怎么走"变成可自动加载的命令序列与索引 | 3 个技能、228 行手册 | 三处蒸馏副本重复且已漂移 |

这里有一个值得单独记录的发现：任务板的状态词是**双写的**——`completed` 56 条，`done` 15 条。同一个概念两种拼法，意味着所有统计、回填、派生脚本都要兼容两套词，任何一次口径判断都可能不一致。这属于典型的数据卫生债。

第二个发现更严重：**12 条 `pending` 任务的 `acceptance.status` 全部是 `draft`**。而仓库自己的规则是"无 ready AC 不开工"（GOV-PROTO-004 与 GC-task-acceptance 都这么写）。两条规则叠加的结果是：任务板上**没有任何一条任务可以合法开工**。这解释了为什么最近三天的提交全是 `fix/*` 而不是 `T-xxx`——不是 AI 不愿意做任务，是规则把门锁上了。

### 1.4 三个关键设计选择

抛开体量，这套流程里有三个设计选择是真正有价值的，值得在后续通用化中保留：

**第一，规则按"有没有执行者"分类。** AGENTS.md 第 10 节是一张"规则 → 机械执行者 → 自查命令"的映射表，并明确标注哪些条目是"约定"（例如"慢命令不阻塞"没有强制手段）。多数仓库写五十条规则，实际生效三条，却从不说破；这里至少承认了这个事实。

**第二，完成定义是执行出来的。** `gov-task-done.sh` 逐条执行：目标文件是否存在、原型文案是否匹配、验收命令是否通过，然后把结果写成带 commit SHA 的证据。设计意图是让"我做完了"这句话失去效力，只有脚本输出有。

**第三，成本感知。** `gov-local-ci` 按变更路径选车道（改文档不跑 gradle），合并队列把"每分支冷构建五到十分钟"换成"一批一次验证"。这是从"流程正确"到"流程划算"的一步，也是开源生态里几乎没人做的一层。

## 2. 文档体系：docs/ 与 Notion 的分工

### 2.1 docs 的七种职能

docs 不是给读者看的说明书，而是给机器和"下一个 AI"读的执行记忆。按被谁消费来分类，它承担七件事：

| 职能 | 落点 | 消费者 | 强制机制 |
|------|------|--------|----------|
| 决策记忆（为什么） | `docs/ai/decisions/DEC-*` | AI 写码前查原因 | lifecycle-audit 要求源码变更带 DEC |
| 任务摘要（做了什么） | `docs/ai/lifecycle/03_TaskGraph.md` | 人看进度、AI 对齐波次 | GOV-DOCS-004 计数必须等于任务板 |
| 交接记忆（从哪接手） | `docs/ai/inbox/`、`.cache/context.jsonl`、`STATUS.md` | 新会话首屏 | 未读信中继；context-load |
| 规格镜像（要做什么） | `docs/ai/lifecycle/01_PRD.md` | AI 确认范围 | GOV-DOCS-003 缺真源声明即 ERROR |
| 规范（怎么写对） | `docs/guides/GC-*`、`docs/ai/guides/*` | AI 动手前的操作手册 | GOV-DOCS-001 未收录索引即 ERROR |
| 黄金标准（定稿事实） | `docs/architecture|guides|reference|changelog` | 最终权威 | 只能通过 promote 晋升，禁止直改 |
| 评审产出 | `docs/ai/reviews/` | 人回看历史判断 | 无强制，已事实停更 |

关键在最后一句：**这些文档是门禁的输入，不是阅读材料**。`gov-validate` 用五个模块专门校验文档自身结构，写错文档等于让提交流程变红。DEC-057 把这条讲得很直白：AGENTS.md 写了不等于被 AI 执行，所以改成 validator 强制。

### 2.2 Notion 的角色与五问判据

`docs/index.md` 的真源声明写得很清楚：仓库与 Notion 是分工关系，不是备份关系。产品范围与验收标准的权威在 Notion，工程决策、架构、规范、原型、任务与治理脚本的权威在仓库。

判据是五个问题，按顺序问，第一个"是"的那行决定归属：

| 序号 | 问题 | 归属 | 理由 |
|------|------|------|------|
| 1 | 被脚本、钩子或 CI 读取吗 | 仓库 | 放 Notion 治理直接失效 |
| 2 | 需要非技术角色编辑吗 | Notion | 不该要求会写 markdown 才能改需求 |
| 3 | 必须与代码同一个 PR 变更吗 | 仓库 | 否则文档与代码必然脱节 |
| 4 | 需要状态、评论、协作、看板吗 | Notion | 仓库做不到 |
| 5 | 要回溯"这个构建依据哪份文档"吗 | 仓库 | git commit 钉得住，Notion 钉不住 |

这里有一个值得记住的判断：**仓库侧是承重的，Notion 是可重建的**。Notion 不可用时，从仓库能重建骨架（链路、AC 编号、任务追溯、DEC 都在）；仓库 docs 不可用时，校验直接红、编号断链、AI 失去指引。所以仓库侧规矩必须更严，Notion 侧只要求一条软规则：结论必须能落到仓库。

### 2.3 三个实际缺口

**缺口一：对照索引还在未合并分支。** `REF-notion-index.md` 记录了 74 个 Notion 页面与仓库路径的对应关系，但 `git log master -- docs/reference/REF-notion-index.md` 为空，说明它只存在于 `origin/cursor/notion-index-467c`。这意味着"不打开 Notion 也能定位对应文件"这个设计目标目前没有生效。

**缺口二：真源声明只强制两个文件。** `gov_validate_docs.py` 的 `MIRROR_DOCS` 只包含 `docs/index.md` 与 `01_PRD.md`。其余可能的镜像（测试策略、发布流程）没有声明，最容易变成"两份互相矛盾的最终结论"。

**缺口三：目录职责重叠。** `docs/prototype/` 下没有任何 markdown，真正的原型在 `design/prototypes/`。新 AI 按目录名去找会扑空。

另外两处规则与执行不一致也值得记录：`docstandard.md` 要求技术文档至少含一张 ASCII 图或 mermaid 图，但多数 DEC 并没有；`docs/ai/reviews/` 保留了多 AI 评审的目录结构，但最新一份停在 10-22，而 `docs/ai/guides/workflow.md` 仍把"R 多 AI 评审"列为十步生命周期之一。

## 3. 开源对照：十三个维度

### 3.1 对比口径

本节的对照对象限于 2026 年仍在活跃维护、且公开可查的方案：GitHub Spec Kit、OpenSpec、BMAD Method、Superpowers、Task Master、Beads、OpenHands 与 SWE-agent 体系。对于非开源的 Kiro、Devin、Jules，只在必要处作为基线提及，不参与评分。

评分不采用"哪个更好"这种无意义的口径，而是拆成十三个可判定的维度，每个维度只问一个问题：**这个维度上，谁有机制、机制是软的还是硬的、能不能被机器验证**。

### 3.2 六类方案的机制表

| 方案 | 规格载体 | 任务模型 | 并发协调 | 强制力 | 完成判定 | 上下文接力 |
|------|----------|----------|----------|--------|----------|------------|
| Spec Kit | spec / plan / tasks / constitution | tasks 勾选，顺序实现，converge 补缺口 | 无机制，靠分支 | 无钩子，人 review | 任务勾完加人看 | 每阶段一份 markdown |
| OpenSpec | 活规格库加变更 delta | 变更级，棕地优先 | 无机制 | 无钩子，drift 靠人 | delta 被接受 | 规格在仓库 |
| BMAD | PRD、架构、story 文件 | 六角色、四阶段、DoR 门 | 无机制，角色串行 | 角色自审（软） | Gates 通过 | story 自带完整上下文 |
| Superpowers | 计划文件、每任务 brief、ledger | 子代理逐任务加逐任务评审 | 子代理隔离加 worktree | 提示词（软），有技能自评 | 完成前验证技能 | ledger 任务账本 |
| Task Master | PRD 到 tasks.json | 依赖、优先级、复杂度、子任务 | 无机制 | 无 | status 字段自报 | tasks.json 持久化 |
| Beads | 依赖图 issue（Dolt/JSONL） | 依赖图加 ready 查询 | hash ID 加认领加多机 | 无钩子 | audit trail | compaction 记忆衰减 |
| OpenHands 与 SWE-agent | GitHub issue | benchmark 实例 | 沙箱隔离 | 无（评测非治理） | 测试通过率 | trace 回放 |

### 3.3 十三维裁定

| 维度 | 本仓做法 | 最接近的开源方案 | 裁定 |
|------|----------|------------------|------|
| 规格可验证性 | 原型 HTML 逐字比对文案与色值 | 无（其余 spec 都是人读的文档） | 领先 |
| 任务模型 | tasks.json 加 BDD 验收加 verify_commands | Task Master 更易用；Beads 依赖图更成熟 | 持平 |
| 依赖与阻塞发现 | parallel plan 分批 | Beads 的 ready 查询成熟得多 | 落后 |
| 并发协调 | 目录锁加 worktree 上限加单一写者 | Beads 多机认领 | 单机领先，多机落后 |
| 强制力 | 三层钩子加 hooksPath 统一加负向测试 | 无对手 | 明显领先 |
| 完成判定 | task-done 执行验收并写 SHA 证据 | 无 | 独有 |
| 规格漂移检测 | 计数一致、断链、时效、文案匹配率 | OpenSpec 的 drift 是概念加人工 | 领先 |
| 上下文接力 | inbox 加 context 加 STATUS 加 DEC | Beads compaction、BMAD story | 持平 |
| 成本控制 | 车道、批次验证、后台执行 | 无 | 领先（近独有） |
| 行为验证 | e2e 需真机，不进 local-ci | SWE-bench 系 | 落后 |
| 输出质量度量 | 只有提交数与测试数 | OpenHands Index、SWE-bench、AgentLens | 明显落后（最大缺口） |
| 可移植性 | 16k 行 shell，绑单仓单 IDE | Spec Kit 与 OpenSpec 支持 30 多个工具 | 明显落后 |
| 规则生命周期 | 五问、退役条件、隐失效防护、负向测试 | 无等价物 | 独有 |

### 3.4 四个"看着像、本质不同"

**其一，与 Spec Kit 和 OpenSpec 比：规格是文档还是断言。** 两者都主张规格先行，但它们的 spec 与 delta 是自然语言，符合性靠人 review。本仓把规格落到 HTML 原型，并用脚本量出文案匹配率、检测硬编码颜色。这是把符合性从"人判断"变成"机器判定"。代价同样清楚：只能验形状，验不了行为。领先项与落后项同源。

**其二，与 Beads 比：任务记忆是数据库还是锁加文件。** Beads 把任务当数据库：Dolt 存储、hash ID 防撞号、四类依赖、ready 查询、compaction 压缩旧任务、多机共享。本仓把任务当锁加文件：目录原子锁、JSON 任务板，冲突靠单一写者与批次队列结构性消除。Beads 赢在规模，本仓赢在门禁。

**其三，与 Superpowers 和 BMAD 比：方法论封装是软还是硬。** Superpowers 的技能库在方法论质量上高于本仓的三个技能，例如它的 TDD 铁律要求"先看测试红，没看到红就等于没测"，比"原型文案匹配"更接近工程本质。但它们是提示词，AI 不执行就什么也不会发生。本仓是可执行程序。取舍是：前者换来可移植与深度，后者换来确定性、牺牲移植性。

**其四，与 OpenHands 比：坐标不同，可以叠加。** OpenHands 是 agent 运行时加评测体系，本仓是流程治理。一个回答"能不能把活干对"，一个回答"流程能不能约束住"。两者正交。本仓恰好缺前者。一个外部证据值得记录：AgentLens 对 2,614 条 OpenHands 轨迹的分析发现，约 10.7% 的"通过"属于 Lucky Pass——回归循环、盲目重试、缺验证。连"测试绿"都不足以证明正确，而本仓连这层度量都还没有。

### 3.5 定位

用两个平面看，位置非常清楚：

```
强制力（软到硬）
  硬 |                    [ lightweigh ]   <- 空位：硬强制 + 可验证
     |
  软 |  BMAD  Superpowers  Spec Kit  OpenSpec  Beads
     +-------------------------------------------------
        人读文档  <---- 规格可验证性 ---->  机器可判定

可移植性（低到高）
  高 |  Spec Kit  OpenSpec  Superpowers  Beads
     |
  低 |        [ lightweigh ]
     +-------------------------------------------------
        无度量    <---- 输出质量度量 ---->   有评测
```

结论是：在"强制力乘可验证性"这个平面上，本仓处在开源生态的空位，这是真实的差异化；在"可移植性乘质量度量"这个平面上，它是明显的洼地。

### 3.6 三个原创点与三个站不住的点

**站得住的三个原创点：**

第一，批次验证。N 个分支合成一个候选，只验证一次。开源默认每 PR 一次 CI，没有人从"集成风险在组合而不在孤立分支"这个角度重构成本模型。

第二，原型可验证化。把 UI 规格变成可断言的文案与色值集合。所有开源 SDD 方案都停留在 markdown。

第三，规则生命周期。五问设计约束、退役判定、负向测试、隐失效防护。这是把治理当工程设计，开源里只有 Superpowers 对"技能自身"做过类似的评测臂。

**站不住的三个点：**

第一，任务、依赖、记忆三块在自建轮子。Beads 与 Task Master 已经做得更成熟，继续维护 83 条 JSON 的手工扩展字段，边际收益在下降。

第二，完成判定只验存在，不验行为。task-done 检查文件在不在、文案对不对、命令跑不跑，却不回答"这个屏幕点得通吗"。这是质量链上唯一的断点。

第三，没有质量度量，一切改进无法证明。流程加了 71 条决策、45 个脚本，却没有任何指标能说明"加了这些之后 AI 交付的正确率上升了"。

## 4. 通用化设计：七个原语与五层架构

### 4.1 资产三分类

做通用化的第一步不是抽象，而是分类。把现有资产逐项问一句：换仓库、换语言、换团队规模，它还成立吗。

| 现有资产 | 通用核（原语级） | 适配层（随栈变） | 不可移植（本仓特有） |
|----------|------------------|------------------|----------------------|
| 任务板与 AC | 任务是工作单元，带可执行验收 | 字段扩展（prototype_ref、wave） | 83 条具体任务与编号 |
| 目录锁 | 认领必须原子互斥 | 后端（本地目录或远程租约） | 路径与 TTL 常量 |
| worktree 隔离 | 一任务一隔离工作区 | VCS 适配（worktree、容器、沙箱） | 上限 3 与命名前缀 |
| 提交钩子 | 快层门禁在提交前 | 钩子机制（git、CI、IDE） | Kotlin 编译等具体检查 |
| 风险车道 | 验证深度随变更面缩放 | 路径到车道映射 | gradle 任务名 |
| 批次队列 | 验组合而非验分支 | 集成后端（直推或 PR） | wf-queue 实现 |
| 原型比对 | 符合性探针接口 | 探针实现（HTML、OpenAPI、schema） | 文案匹配率阈值 |
| DEC 与 inbox | 决策记忆与交接记忆 | 存储（文件、Notion、Beads） | 中文文档规范 |
| 规则五问与退役 | 元规则 | 无 | 具体决策内容 |
| 治理总开关 | 可审计的有期逃生口 | 无 | 两小时与八小时常量 |

三个最容易被误判成通用的东西：单机信任（团队场景直接失效，必须双模）、HTML 原型（通用的是探针接口，不是原型格式）、文档即门禁（框架只应承认有执行者的规则）。

### 4.2 七个原语

这是整个通用设计的承重墙，判断标准只有一条：换仓库、换语言、换团队，原语不变。

| 编号 | 原语 | 不变量 | 最小接口 | 开源对照 |
|------|------|--------|----------|----------|
| 1 | Task | 工作单元是带可执行验收的任务，不是对话 | id、scope、acceptance、status | Task Master、Beads |
| 2 | Claim | 开工前必须原子占位，带 owner 与 TTL | claim 返回租约或冲突 | Beads 更成熟 |
| 3 | Isolation | 一个认领对应一个隔离工作区 | open 返回 workspace | Superpowers |
| 4 | Probe | 规格符合性是可执行探针，不是文档 | check 返回通过、得分、发现项 | 无，本仓原创 |
| 5 | Gate | 门禁分快、慢、批次三层，深度随风险缩放 | gate 返回车道与结果 | 无，本仓原创 |
| 6 | Evidence | 完成等于命令执行记录加 commit SHA | evidence 返回记录 | 无，本仓原创 |
| 7 | Memory | 决策与交接必须外置且可重建 | decide、handoff、resume | Beads、BMAD |

### 4.3 两条元规则

元规则必须写进框架本体，而不是留在文档里：

**M1，规则三件套。** 任何规则必须同时提供机械执行者、负向测试（证明它真会拦）、退役条件（两次误伤或 N 天零命中即进入退役评审）。缺一项的规则不允许进入框架。开源方案几乎全部缺这条，所以它们的规则会烂掉；本仓有雏形，但还没把它变成框架级约束。

**M2，有期逃生口。** 任何门禁必须提供带 TTL、带审计日志的关闭通道。没有逃生口的门禁最终会被 `--no-verify` 绕过，等于不存在。

### 4.4 五层架构

```
┌─ L4 代理面 ───────────────────────────────────────────────┐
│ AGENTS.md（生成，不手写）+ Skills（薄壳）+ MCP Server       │
└──────────────────────────┬────────────────────────────────┘
┌─ L3 策略（每仓一份 flow.yaml）────────────────────────────┐
│ 车道映射 / 必需门禁 / 阈值 / 豁免人 / 集成模式              │
└──────────────────────────┬────────────────────────────────┘
┌─ L2 适配器（可插拔）──────────────────────────────────────┐
│ vcs / isolation / verify / probe / memory / integrate / eval│
└──────────────────────────┬────────────────────────────────┘
┌─ L1 运行时（CLI，全部 --json）────────────────────────────┐
│ init / plan / start / verify / finish / queue / doctor / eval│
└──────────────────────────┬────────────────────────────────┘
┌─ L0 协议（JSON Schema，不含代码）─────────────────────────┐
│ task / lease / evidence / gate-result / decision / handoff  │
└───────────────────────────────────────────────────────────┘
```

层间约束决定它会不会长成第二个产品：L0 只有 schema；L1 不许 import L2 实现；每个适配器必须能空实现以保证零依赖可跑；L3 是唯一允许出现项目特有概念的地方；L4 全部由 init 生成，项目不得手改。

### 4.5 策略文件与适配器接口

策略文件是唯一的项目配置，长这样：

```yaml
version: 1
mode: solo            # solo | team
integration:
  adapter: git-queue  # git-queue | github-pr | gitlab-mr
isolation:
  adapter: worktree
  limit: 3
lanes:
  A: ["docs/**", "design/**", ".ai/**"]
  B: ["src/**", "app/**"]
  C: ["**"]
verify:
  A: []
  B: ["npm test"]
  C: ["npm run build", "npm test", "npx tsc --noEmit"]
probes:
  - name: api-contract
    adapter: openapi-lint
    spec: "api/openapi.yaml"
    blocking: true
memory:
  adapter: files
rules:
  - id: no-direct-main
    stage: pre-commit
    negative_test: "tests/flow/test_no_direct_main.py"
    retire_if: zero_hit_30d
```

适配器接口只需要八个方法：

```text
Vcs        commit / push / integration_branch / protected
Isolation  open / close / list
Verify     run(lane) / estimate(lane)
Probe      check(spec, code) -> {pass, score, findings}
Memory     decide / handoff / resume / compact
Integrate  enqueue / verify / merge / cleanup
Eval       suite / run -> {pass_rate, cost, trace}
Surface    emit_agents_md / emit_skills / mcp_tools
```

注意 `Integrate` 的双模：本地队列与 PR 流程是同一个接口的两个实现，上层完全无感。这是"通用"能否成立的关键一步，也是本仓当前最缺的一环。

### 4.6 六条硬约束

| 序号 | 约束 | 反面教材 | 具体要求 |
|------|------|----------|----------|
| 1 | 零新 DSL | 自造 YAML 工作流语言，用户要先学它 | 一切是文件加命令加 JSON 输出 |
| 2 | 渐进可用 | 装完先配十个文件才能跑 | init 后立刻能 start，缺什么标 skipped |
| 3 | 双模同一 CLI | 单人方案进团队即废 | 只差一行配置加一个适配器 |
| 4 | 规则三件套 | 规则只增不减，最终被绕过 | 加规则时强制三者齐备 |
| 5 | 状态厂商中立 | 状态锁在某 SaaS，换工具即失忆 | 纯文本加 schema，任何工具可读写 |
| 6 | 成本一等公民 | 每个任务跑全量 CI | 车道、批次、后台、预算上限 |

第四条是能否长期存活的关键，第六条是唯一真正领先的地方，必须做成核心卖点而非附加功能。

### 4.7 通用性验证方案

通用的门槛不是"能跑"，而是"在没有为它优化过的仓库里能跑通"。验收必须用试点，不能用自家仓库。

三个试点仓：绿地 TypeScript Web（打爆"原型即规格"与 gradle 车道）、棕地 Python 服务（打爆"任务板从零建"与单一写者）、本仓 Android（回归基线）。每个试点至少两个不同厂商的 agent，跑二十个真实任务。

五个指标：首次可用时间小于十分钟；证据覆盖率大于九成；门禁误伤率小于百分之五；单位任务验证成本比全量低六成；**流程 eval 通过率在换模型或换提示词后不下降**。

最后一条是唯一能对外讲的故事。此外应建一个 fixture harness：一组假仓库，每个注入一种违规（直提主干、未认领开工、证据缺失、跨任务改文件），断言门禁确实拦下。这相当于把现有的负向测试升级成流程级回归。

### 4.8 迁移四步

第一步，抽协议不改代码：从现有脚本抽出六个 schema，写一张"脚本到原语"的映射表。验收标准是不改任何现有脚本，流程照旧跑绿。

第二步，CLI 薄壳只在自家仓试用：七个命令，全部 JSON 输出，内部先包一层现有脚本，不重写。验收是连续二十个真实任务用新 CLI 完成。

第三步，适配器化并接入第二个试点：把 worktree、gradle、原型比对、文件记忆全部下沉。禁止为试点修改 L0 与 L1，只能写适配器与策略文件。验收是试点仓的策略文件里不出现任何 Android 概念。

第四步，评测层与分发：任务到期望改动集与期望测试结果的映射，支持两次运行对比；一行安装，升级只覆盖框架拥有区。

## 5. 分层优化：九个层面的现状与动作

这一节只针对本仓，不谈通用化。核心判断是：问题不是缺层，而是有三层在空转、两层自相矛盾、一层完全没有。

### 5.1 总表

| 层 | 现状 | 判决 |
|----|------|------|
| L1 入口与指令面 | 三套蒸馏规则，其中一份还在写"反思不少于五十字是硬约束"（该机制已退役） | 自相矛盾 |
| L2 任务与规格 | 12 条 pending 全是 draft 验收，规则把板子锁死；状态词双写 | 自我阻塞 |
| L3 并发与隔离 | 锁、worktree、单一写者已成体系 | 基本健康 |
| L4 门禁与合入 | 三层钩子齐全，但无远程权威；钩子体检只在慢层跑 | 有洞 |
| L5 完成与证据 | 证据目录根本不存在，最强宣称从未产生过一条证据 | 空转 |
| L6 验证与度量 | 1,155 个测试，0 个度量输出质量的指标；多 AI 评审停更 | 完全缺失 |
| L7 记忆与文档 | 对照索引在未合并分支；空目录；十步流程文档已废弃 | 漂移 |
| L8 治理自身 | 16k 行，无调用频率统计，无退役执行 | 待减重 |
| L9 成本 | 单日 244 次提交，9 个 PR 只产出 1 个产品改动 | 浪费明显 |

### 5.2 P0：先修空转与自相矛盾

**完成证据要真的跑起来。** `gov-task-done.sh` 会写 `.ai/evidence/<ID>.json`，`wf-autopilot` 也会读它，但仓库里这个目录不存在，`ls` 直接报错。这说明要么从未成功执行，要么执行后被删或未入库。无论哪种，"完成有证据"目前是空的。动作三条：证据入库；缺证据从警告升级为拒绝合入；证据补执行时间、执行者、环境三个字段。

**任务板要能开工。** 12 条 pending 全部 draft，等于零可开工任务。逐条处置：能补的补成 ready，需要人类答复的显式标 blocked 并写 open_questions，不做的标 cancelled，不留 draft。同时统一状态词，并在校验里拒绝旧词。再加一条板子健康度检查：draft 加 blocked 占比过高时警告，提示的是"板子失效"，而不是"某条任务不合格"。

**删掉会撒谎的文件。** `.opencode/rules.md` 仍在写"反思必须不少于五十字，这是硬约束，不写无法提交"，而该机制早已拆除。这正是仓库自己在 10-22 审计里批过的"三套真相"复发。动作：蒸馏文件降级为指针加三条硬约束，不再复制规则正文；`workflow.md` 的十步流程退役或重写为四个命令；加一条校验，蒸馏文件里出现"硬约束""必须""禁止"却在 AGENTS.md 第十节找不到执行者即判失败。

**把隐形失效挡在快层。** 钩子体检从慢层提到提交前（它是毫秒级检查）；确认治理总开关不能关掉慢层门禁（快层可关，慢层绝不可关）；在主干上的跳过必须额外记录原因，否则审计无法区分测试与真绕过。

### 5.3 P1：补最缺的两层

**度量层。** 四个指标先进指标文档：证据覆盖率、门禁误伤率、验证平均耗时、任务返工率（同一任务被重开次数）。然后建最小 eval 集二十条，每条是一句需求加期望改动文件集加期望通过测试，跑两次对比。再往上，用截图或预览快照替代真机走查的八成场景。第二项成本约三天，是全局投入产出比最高的一件事。

**执行层。** `dev-verify` 目前依赖真机，没设备就断链。加无设备路径：编译加 JVM 测试加截图回归。同时开 Gradle 配置缓存与构建缓存，并把"从改动到绿灯"的实际耗时记进指标。明确验证预算：快车道十秒、中车道三分钟、全量十分钟，超过预算视为设计问题而不是"再等等"。

**记忆层。** 把对照索引合入主线；删掉或标注空的原型目录；明确真源声明只覆盖哪几个文件，避免中间态；约束目录要么填五条真约束要么删除。

### 5.4 P2：结构减重

治理自身的减重分三件事：脚本调用频率统计（跑三十天，输出零命中清单）；退役执行（沿用既有口径，目标脚本数下降四分之一以上）；规则三件套元数据（建一张表，规则对应执行者、负向测试、退役条件，并与 AGENTS.md 第十节互相校验）。最后按第四章的分类把与 Android 强绑的部分下沉为适配器，为将来的通用化铺路。

成本层三条：控制提交粒度，一个任务一个 PR 一个可验证单位；批次队列常态化，同一天同模块的分支主动攒批；把验证耗时可视化，让"这次合入花了多少分钟"成为可见成本。

### 5.5 优先级总表

| 优先级 | 层 | 动作 | 成本 | 验收 |
|--------|----|------|------|------|
| P0 | L5 | 证据入库、缺证据拒绝合入、补三字段 | 半天 | 证据目录有五个以上含 SHA 的文件 |
| P0 | L2 | 12 条 draft 处置 | 半天 | 状态查询有可开工任务 |
| P0 | L2 | 状态词统一并拒绝旧词 | 半天 | 旧词计数为零 |
| P0 | L1 | 删失效规则，降级为指针 | 1 小时 | 全文检索无残留 |
| P0 | L1 | 十步流程退役 | 2 小时 | 与 CLI 帮助一致 |
| P0 | L4 | 钩子体检进快层、确认慢层不可关 | 2 小时 | 关开关后慢层仍跑 |

| P2 | L8 | 规则三件套元数据 | 3 天 | 与手册一一对应并被校验 |

## 6. 风险、盲点与不做什么

### 6.1 五个盲点

行为正确性没有机器证据；规格漂移只检测文档侧不检测语义侧；AI 输出质量无度量（换模型后无法判断好坏）；文档与程序存在多处不一致（十步流程、蒸馏规则、空目录）；人类动作（真机验收、新机型回归）没有进任务板阻塞项。

### 6.2 不做的四件事

不要继续加规则——现在的问题不是规则不够，而是有三层没跑起来；不要重写脚本——P0 全是让已有机制生效；不要把评审目录重新激活成常规流程——它在 10-22 之后自然消亡，说明对当前节奏没有价值，要激活只在架构变更与门禁变更这两个节点用；不要在 P0 完成前做通用化——把空转的机制抽象出去，等于把 bug 一起抽象。

### 6.3 失效模式清单

这套流程已经出现过、并且还会再出现的失效模式，值得单列：机制存在但从未执行（证据目录）；规则叠加导致死锁（draft 验收加无 ready 不开工）；同一规则三处副本各自漂移（蒸馏文件）；度量口径错误产出假警告（原型匹配率作用域）；门禁绕过无痕（跳过日志不记原因）；文档描述与程序行为不一致（十步流程）。

## 7. 结论与下一步

一句话总结：**这套流程的真实坐标是"在硬强制加可验证规格这个开源生态尚无人占据的空位上，用一万六千行自研脚本，为单一仓库做了一个高度定制、几乎不可移植的交付纪律系统"。它比多数开源方案更硬、更严，但少了一整层输出质量度量。**

因此优化顺序必须是：先修回路（证据、任务板、指令面），再补空白层（度量与行为验证），最后才谈减重与通用化。

## 附录 B：术语表

| 术语 | 含义 |
|------|------|
| 四平面 | 指令面、执行面、事实面、验证面 |
| 原语 | 与语言和框架无关的最小机制单元，本笔记定义七个 |
| 探针 | 把规格变成可判定断言的适配器，如原型文案比对、OpenAPI 校验 |
| 车道 | 按变更路径决定验证深度的分级，A 秒级、B 分钟级、C 全量 |
| 批次验证 | 多个分支合成一个候选，只验证一次组合结果 |
| 证据 | 验收命令的执行记录加 commit SHA，写入 `.ai/evidence` |
| 规则三件套 | 执行者、负向测试、退役条件，缺一不可 |
| Lucky Pass | 测试通过但过程存在回归循环或缺失验证的"侥幸通过" |
