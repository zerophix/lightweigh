# DEC-078: DDD 架构重构 —— 修复领域模型贫血，领域逻辑下沉 Domain 层

> 2026-10-27 实测：Domain 层仅 650 行（占 1.4%），核心体成分计算、风险评估、建议生成全在 Application 层（BodyAnalysis.kt 390 行），违反 DDD 核心原则。

---

## 背景与问题

### 现状分析（代码证据）

| 层 | 代码行数 | 占比 | 核心问题 |
|---|---|---|---|
| **app (UI)** | 39,103 | 87% | 原型驱动、Compose 组件、文案对齐 |
| **application** | 3,600 | 8% | **吸收了本该在 Domain 的计算逻辑** |
| **infrastructure** | 2,900 | 6.5% | 真实适配器（BLE、Room、CloudBase） |
| **domain** | 650 | 1.4% | 仅有算法和接口，**领域模型贫血**（只有 getter/setter） |

### 具体违规证据

1. **BodyAnalysis.kt (390 行)** 在 `application/query` 包中包含：
   - 体脂率/肌肉率/骨量/水分/内脏脂肪/基础代谢/身体年龄 计算公式
   - 7 大健康风险评估（肥胖/脂肪肝/高血压/糖尿病/骨质疏松/高血脂/痛风）
   - 3x3 体型分类矩阵（消瘦型/苗条肌肉型/隐形肥胖型...）
   - 所有健康建议文案生成

2. **MeasureSession.kt (913 行)** 在 `application/measure` 包中：
   - 纯编排逻辑，**零领域决策**，只调用 `RecordMeasurementService` 落库

3. **领域模型类** 仅为数据容器：
   - `MeasureRecord.java`: 只有字段 + getter
   - `HealthLog.kt`: 1 个方法
   - `Member.kt`: 3 个方法
   - `Habit.kt`: 1 个方法

---

## 决策

### 核心原则
1. **领域逻辑下沉**：所有业务规则、计算公式、风险评估、分类判定、建议生成 → `domain/service/`
2. **领域模型充血**：`MeasureRecord`、`HealthLog`、`Member`、`Habit` 添加业务行为方法
3. **Application 层变薄**：仅做编排、事务、端口调用，**不包含业务计算**
4. **验收标准升级**：从"构建级"（仅跑单测）升级为"功能级"（黄金向量、真机验收）

### 目标架构

```
┌─────────────────────────────────────────────────────────────┐
│  app (UI)          ← 原型驱动、文案对齐、状态呈现             │
├─────────────────────────────────────────────────────────────┤
│  application       ← 编排、命令/查询、端口调用、事务边界       │
│  - BodyAnalysisQuery → 调用 BodyCompositionService           │
│  - MeasureSession  → 编排 BLE + 调用 MeasureRecord.calculate()│
├─────────────────────────────────────────────────────────────┤
│  domain            ← **业务核心**（目标：占比提升到 15%+）     │
│  - service/                                                  │
│    ├── BodyCompositionService       # 体成分计算              │
│    ├── HealthRiskAssessmentService  # 健康风险评估            │
│    ├── BodyShapeClassificationService # 体型分类              │
│    └── HealthAdviceService          # 健康建议生成            │
│  - model/                                                    │
│    ├── MeasureRecord.calculateBodyComposition()              │
│    ├── MeasureRecord.assessHealthRisks()                     │
│    ├── MeasureRecord.classifyBodyShape()                     │
│    ├── HealthLog.getTrendAnalysis()                          │
│    ├── Member.canStartMeasurement()                          │
│    └── Habit.isDueToday()                                    │
├─────────────────────────────────────────────────────────────┤
│  infrastructure    ← 适配器实现（BLE、Room、CloudBase、SDK）  │
└─────────────────────────────────────────────────────────────┘
```

## 方案评分

| 方案 | 评分 | 说明 |
|---|---|---|
| **方案 A：领域逻辑下沉 + 模型充血（采纳）** | 5/5 | 符合 DDD 核心、可测性最强、复用性最高、治理可验证 |
| 方案 B：保持现状、只补测试 | 2/5 | 架构腐化不可逆、验收仍为构建级、后续扩展成本指数级 |
| 方案 C：引入 Anemic Domain Model 承认者模式 | 3/5 | 妥协方案，不解决根本问题、只是给贫血找借口 |

| ID | 假设 | 依赖条件 | 失败影响 | 验证状态 |
