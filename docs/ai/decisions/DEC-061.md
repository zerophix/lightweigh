# DEC-061: Wave 1 新屏以呈现式组件交付，静态文案与运行时读数分离

> 任务目标文件只列 Screen，故本轮不新建四件套；配套地把原型文案抽为 MetricSpec 常量、测量值留在 MetricReading，避免"改读数顺手改参考区间"的事实漂移。

---

## 决策

### 背景与冲突

`GC-coding-conventions` 规定「新页面 = 新目录 + 四件套（Screen/ViewModel/UiState/Route）」，
但 T-081 / T-082 的 `target_files` **只列了 Screen 文件**，且两者所在的
`feature/history`、`feature/trend` **已有** `HistoryViewModel`、`TrendViewModel`。

两种做法的取舍：

| 做法 | 问题 |
|------|------|
| 严格建满四件套 | 超出任务声明的 `target_files`；与既有 ViewModel 职责重叠（两套历史数据源）；Wave 2 的 T-077/083 要改同目录，新增文件抬高冲突面 |
| 只交付 Screen | 不符合四件套默认约定，需明确授权 |

### 决策内容

1. **本轮只交付呈现式 Screen**：状态由**既有** `HistoryViewModel` / `TrendViewModel` 汇总后经参数传入，
   Screen 不新建 ViewModel、不直接取数（仍满足「Screen 纯渲染、不访问 repository」这条硬约束）。
   四件套的补建留给**接线任务**（Wave 2 修改既有屏时一并决定），避免本波与 Wave 2 抢文件。
2. **静态文案与运行时读数分离**（T-082）：
   - `MetricSpec`：标题、单位、解释段、参考区间、分级、公式、免责 —— **逐字来自原型**，属产品事实
   - `MetricReading`：本次测量值、差值、趋势点 —— 运行时数据
   分离的直接收益：文案匹配率实测 83%（Wave 0 薄封装组件仅 5%~28%），
   且改测量值不可能顺手改掉参考区间。
3. **AC-HT4 / AC-HT5 落为纯函数**：
   - `segmentSeries()` 把含缺日的序列切成互不相连的分段，**逐段绘制 → 结构上不可能产生跨空洞插值线**
   - `trendStateOf()` 判定 `Empty / InsufficientData / Plottable`，非 `Plottable` 时不渲染任何趋势线
   两者均由 JVM 单测钉死，不依赖视觉走查。
4. **编辑约束同理落为纯函数**：`isEditable()` + `validateRecordEdit()`
   （测量字段不可改、recordId 必须同源），保存前调用即可阻断违规写入。

### 明确不动的

- 不新建 `HistoryDetailViewModel` / `Route`（接线属 Wave 2 范围）
- 不改动 `HistoryScreen`、`TrendScreen` 等既有文件（Wave 1 只新建）
- 不改 `QkAreaChart` —— 缺日切段在调用侧完成，图表组件保持通用

## Assumptions

| ID | 假设 | 依赖条件 | 失败影响 | 验证状态 |
|----|------|----------|----------|:--------:|
| A1 | 既有 ViewModel 已能产出详情与指标读数 | 接线时字段够用 | 接线任务需补字段 | 未验证（接线不在本波） |
| A2 | Screen 无 ViewModel 即不构成「数据源二义」 | 单一传参、不自取数 | AC-HT3 同源被破坏 | 已验证（单测覆盖 recordId 同源） |
| A3 | 缺日切段的分段绘制可读 | 分段数通常 ≤2 | 分段过多时图表碎 | 由调用方过滤过碎区间（后续观察） |
| A4 | 原型文案可直接内联为 Kotlin 常量 | 文案非动态、无 i18n 需求 | 多语言需外提 strings | 当前产品仅 zh-CN，见 `.language` |

## 方案评分

| 方案 | 评分 | 说明 |
|------|------|------|
| 只交付 Screen + 文案读数分离（采纳） | 5/5 | 不越 target_files、不与 Wave 2 抢文件、文案匹配 83%、AC 落成可测纯函数 |
| 严格补满四件套 | 2/5 | 超任务范围，且与既有 ViewModel 重复 |
| 文案与读数混在一个 data class | 2/5 | 事实漂移风险，且原型核对困难 |
| 在 Screen 里直接访问 repository | 1/5 | 违反分层硬约束 |

## 执行记录（2026-10-23 · T-102 sync 网络/服务状态页）

T-102 按本决策「只交付呈现式 Screen」的口径落地 `feature/sync/NetworkStatus.kt` 与
`ServiceStatus.kt`，并把 AC-N3「网络检测经由传入回调」落成
`NetworkAvailabilityProbe` / `ServiceAvailabilityProbe`（`fun interface`，由调用方注入实现），
检测结果经 `networkStatusStateOf` / `serviceStatusStateOf` 单向进入不可变
`NetworkStatusUiState` / `ServiceStatusUiState` —— Screen 结构上拿不到系统网络服务
（JVM 单测去注释后断言两文件无 `ConnectivityManager` / `android.net` 引用）。
原型文案抽为 `NetworkStatusText` / `ServiceStatusText` 常量对象，由逐字单测钉住；
两状态页共用 `SyncStatusPage` 版式（T-102 限定只新建两文件，故共版式以 internal
内联于 `NetworkStatus.kt`，同包复用，不另开第三个文件）；探测恢复即不渲染离线文案——
原型没有「已恢复」态文案，不自造，出栈交给调用方。
