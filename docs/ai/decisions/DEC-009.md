# DEC-009: 修复 session-end 上下文缓存静默失败 — PROTO-002 永远无法被自己刷新

> save handoff 漏传必填字段 to，错误被 2>/dev/null + || true 双重吞掉；补字段、agent 检测替代硬编码、加静态契约测试钉住两脚本字段对齐。

---

## 决策

真实执行 session-end 收尾链路（人类批准）时发现：第 4 步「写入上下文缓存」
显示完成，但 .cache/context.jsonl 未新增 handoff 条目，GOV-PROTO-002 仍报
「上次 session-end 超过 36 小时」——**session-end 永远无法刷新它自己负责的那个
时效时钟**。

根因链：`ses-session-end.sh` 调用 `ses-context-cache.sh save handoff` 时漏传
必填字段 `to`（REQUIRED_FIELDS_handoff="from to context next key_files"），
save 返回 1 并向 stderr 报错，但调用处 `2>/dev/null || true` 把错误和失败
双重吞掉，脚本继续走完并打印「交接完成」。

同处发现第二个问题：`from="claude"` 硬编码——opencode session 写出的接力信
一律署名 claude（收件箱 20261014-023008 即为实例），agent 身份失真。

修复：

1. **组 A**：save handoff 调用补 `to="next-ai"`（与 context.jsonl 既有
   handoff 条目的 to 值一致）。
2. **组 B**：`from` 改为环境检测——`OPENCODE=1`（本机实测存在）/`CLAUDECODE`
   （Claude Code 文档行为），无匹配时 `unknown-ai`，不再默认冒充 claude。
3. **组 C**：静态契约测试——解析 ses-context-cache.sh 的
   REQUIRED_FIELDS_handoff 与 ses-session-end.sh 的 save handoff 调用块，
   断言调用覆盖全部必填字段。两脚本字段契约从此单向可查，再漏字段测试即红。
4. 本次修复后手工补写缺失的 handoff 条目（按修复后的正确参数），使
   PROTO-002 立即转绿——该条目即 session-end 本应写入的那条。

## Assumptions

| ID | 假设 | 依赖条件 | 失败影响 | 验证状态 |
|----|------|----------|----------|:--------:|
| A1 | OPENCODE 环境变量是 opencode 会话的稳定标识 | 本机 env 实测 OPENCODE=1 | 署名 unknown-ai | 已验证（本机），跨版本待观察 |
| A2 | CLAUDECODE 是 Claude Code 的环境标识 | Claude Code 文档行为 | Claude 场景署名 unknown-ai | 待验证（下次 claude session） |
| A3 | 静态字段契约测试对脚本重构的鲁棒性可接受 | 字段声明与调用块的文本模式稳定 | 测试需随重构更新 | 已验证（25+1 测试通过） |

## 方案评分

| 方案 | 评分 | 说明 |
|------|------|------|------|
| 补字段 + agent 检测 + 契约测试（采纳） | 5/5 | 修复缺陷、修正身份、钉住契约，三点全收敛 |

| PROTO-002 改读收件箱文件时间 | 1/5 | 绕过缓存层缺陷，接力推理数据继续缺失 |

## 已知局限

- `2>/dev/null || true` 的容错风格在本次掩盖了失败；本次只修契约不改风格
  （改风格影响面大，留待收尾链路整体加固时处理）。
- 契约测试是静态文本解析，脚本大幅重构时需同步调整（A3 已注记）。
- 本缺陷是「收尾链路静默失败」的第一个实锤，不排除链路其他步骤（inbox send、
  STATUS 刷新）有同款吞错——尚未逐段审计。
