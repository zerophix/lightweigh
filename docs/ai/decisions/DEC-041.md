# DEC-041: 统一错误模型与跨模块元数据可见性修复

> 引入 `AppError` / `AppResult` 统一错误模型（DEC-041），并修复 domain 模块元数据在 Android 模块中不可见的根因。

---

## 决策

1. **domain 模块改为 Android Library（`com.android.library` + `kotlin.android`）**：
   - 原因：纯 JVM 模块（`kotlin.jvm`）编译产出的 Kotlin 元数据（`.kotlin_module` + 类文件注解）无法被 Android 模块的 Kotlin 编译器正确消费，导致 `sealed class` 层级、`companion object` 成员（如 `AppError.Codes`）、扩展函数在应用层不可见，编译报「Unresolved reference」「when expression must be exhaustive」。
   - 方案：domain 改为 Android Library（`apply plugin: 'com.android.library'` + `kotlin.android`），仅保留 Kotlin 源码、无资源、无组件、无 manifest 实体组件。产出的 AAR 包含 Android 兼容的元数据注解，应用层编译器可正确识别密封类层级、伴生对象成员、扩展函数。
   - 兼容性：测试仍在 JVM 上跑（`domain:test` 走 `kotlin.android` 的 JVM target），无需 Android 设备/模拟器。

2. **`AppError.Codes` 提升为顶层对象 `AppErrorCodes`**：
   - 原因：`companion object` 内嵌套 `object Codes` 在跨模块元数据消费时不稳定（Android 编译器偶发不识别）。
   - 方案：移至同包顶层 `object AppErrorCodes`，所有引用改为 `import com.xcwk.scalehub.domain.types.AppErrorCodes`。

3. **统一错误模型 `AppError` / `AppResult` 全链路落地**：
   - `AppError` 密封类：`Network`/`Server`/`Validation`/`Business`/`Unknown` 五类，含 `fromDomain`/`fromThrowable`/`Codes` 常量。
   - `AppResult<T>` 密封类：`Ok(data)` / `Err(AppError)`，提供 `map/flatMap/fold/recover/recoverWith/onFailure/getOrThrow/isSuccess`、与 `kotlin.Result` 互操作扩展。
   - 基建层（`CloudBaseGateway`/`CloudFunctionAi`/`SessionStore`）返回 `AppResult`，网络异常、HTTP 非 2xx、JSON 解析失败均显式建模，不再被 `runCatching.getOrNull()` 吞成 `null`。
   - 应用层（`SyncService`/`AuthService`/`AiService`/`RestoreAccountService`/`DeleteAccountService`）签名改为 `AppResult`，错误按类型分流（Network 重试、Server 401 跳登录、Business 直达用户文案）。
   - 敏感信息过滤：`SessionStore.request()` 只记路径不记 query（`verify_code` 等）。

## 方案评分

| 方案 | 评分 | 说明 |
|------|------|------|
| domain 改 Android Library + AppErrorCodes 顶层对象（采纳） | 5/5 | 根治元数据不可见，零运行时依赖，测试不变 |
| domain 保持纯 JVM + 手写元数据注解 | 2/5 | 维护成本极高，易漏标注 |
| domain 发布到 Maven 本地仓库再依赖 | 3/5 | 增加发布步骤，仍可能元数据不全 |
| 放弃统一错误模型，继续各自为政 | 1/5 | 不解决原问题（错误被吞、无法分流） |
