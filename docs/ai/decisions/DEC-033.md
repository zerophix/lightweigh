# DEC-033: CI 成本治理——并发去重、文档变更跳过重型构建、构建缓存与超时上限

> 私有仓库的 Actions 分钟数是计量的，而每次 master 推送都要跑一趟七到十二分钟的
> Android 构建；其中纯文档与治理元数据的推送占了大半，这些轮次不可能因为文档改动而变红。

---

## 决策

事实基础（本会话 master 推送的实测时长）：

| run | 内容 | 时长 |
|-----|------|------|
| 39027280045 | PR #1 合并 | 11m50s |
| 39033640921 | 交接与状态刷新（只改 `docs/`、`.ai/`、`.cache/`、`STATUS.md`、`README.md`、`mkdocs.yml`） | 10m3s |
| 39033818371 | 交接信署名修复（改 `scripts/`、`docs/`） | 7m22s |
| 39035820565 | 本决策落地（改 CI 配置、`gradle.properties`、文档） | 8m19s |

`build-and-guard` 的实质工作是编译 + 单测 + lint + APK + androidTest 源集编译，耗时基本恒定在十分钟量级；
而第二、三轮并没有改任何源码，构建只是重走一遍。真正的成本集中在 `build-and-guard`（`docs-validate`
与 `lifecycle-audit` 都很短）。按同一份日志拆解，`build-and-guard` 里有三段可省的钱：

1. **发行包重下（约 100 秒/轮）**：`Build and test` 步骤 13:15:45 开始
   `Downloading https://mirrors.cloud.tencent.com/gradle/gradle-9.4.1-all.zip`，直到 13:17:26
   才出现第一个任务。根因是 `gradle-wrapper.properties` 用 `distributionBase=PROJECT`
   把发行包放在仓库内 `gradle/dists`（1.7GB，已 gitignore），CI 全新检出必然从零下载。
2. **纯文档轮次的全量构建（约 7~10 分钟/轮）**：不改源码的轮次重走一遍编译与测试。
3. **并行轮次叠加**：本会话曾出现两个 run 同时跑，各烧十来分钟。

采纳四项改动，都落在 CI 配置与一个 Gradle 属性上：

1. **分支感知的并发去重**：`concurrency` 组按 ref 聚合，`cancel-in-progress` 只对
   非 `master`/`main` 为真。特性分支上的新推送作废上一轮未跑完的 run；而权威分支的每一轮
   都必须跑到结论——否则「刚推一个文档提交」就会把上一次代码构建的结论悄悄抹掉（且表面正常）。
   这一条是在本轮实现后自己发现并当场修正的：最初写成 `cancel-in-progress: true`，
   按 ref 聚合意味着 master 上也会互相作废。
2. **变更范围判定**：新增 `Detect change scope` 步骤，用基线提交做 `git diff --name-only`，
   当本次改动只落在 `docs/`、`*.md`、`mkdocs.yml`、`.ai/`、`.cache/` 时，跳过 `Build and test` 与
   `Compile androidTest` 两个步骤。**job 本身仍然执行并上报成功**，因为整 job 跳过会让分支保护上的
   必填检查停在「Expected」而阻塞合并。判定结果与文件清单都打印进日志。
   基线提交不可用（首次推送、强制推送）时一律按「动了代码」处理——宁可多跑一轮，也不留门禁空洞。
3. **构建缓存**：`gradle.properties` 增加 `org.gradle.caching=true`，并新增
   `Report build cache state` 步骤，在构建前打印缓存目录的条目数与大小。
   本轮日志已把落点钉实：CI 上构建缓存在 `/home/runner/.gradle/caches/build-cache-1`
   （Post 步骤自带的 Gradle 调用用 `-g /home/runner/.gradle`，自报
   `Using local directory build cache ... location = /home/runner/.gradle/caches/build-cache-1`），
   而 setup-gradle 会把该用户目录整体纳入 `gradle-home-v1` 缓存并跨提交 `restore-key` 命中
   （本轮日志可见还原成功）。本机则在仓库内 `./.gradle-user/caches/build-cache-1`
   （`gradlew` 第 28 行 `export GRADLE_USER_HOME="$APP_HOME/.gradle-user"`）——两侧落点不同，但各自确定。
   本轮 `FROM-CACHE` 命中 36 次，证明构建缓存已在工作；跨轮存活见 A2。
4. **超时上限**：`build-and-guard` 30 分钟、`docs-validate` 20、`lifecycle-audit` 15、
   模拟器 job 45 —— 封死「挂死烧满 6 小时默认上限」这种最坏情况。

判定逻辑的安全方向已在本机用四个真实历史提交验证过（不靠推断）：

| 样本提交 | 变更内容 | 判定 |
|----------|----------|------|
| `c870b77` | 仅文档 + 状态快照 | `code=false`（跳过构建） |
| `53cb429` | 脚本 + 文档 | `code=true` |
| `4443e4b` | `settings.gradle.kts`（构建配置） | `code=true` |
| `e23a5a7` | 仅 `.github/`（CI 配置） | `code=true` |

构建缓存也在本机实证过：清掉 `domain/build` 再跑 `:domain:compileKotlin`，第二轮输出
`> Task :domain:compileKotlin FROM-CACHE`、`1 actionable task: 1 from cache`。

**未采纳**：

- **删掉 master 的 push 触发，只保留 PR 门禁**：省得最彻底，但 master 失去独立验证，
  且 `lifecycle-audit` 在 push 场景的审计一并丢失。合并后的 master 值得被独立验一次。
- **立刻改发行包落点**（CI 上改写 `distributionBase`／自建 1.7GB 的发行包缓存／改用 `-bin`）：
  收益约 100 秒/轮，但三种改法各有代价（前者取决于 setup-gradle 是否缓存 `wrapper/dists`，
  中者上传开销可能高于收益，后者改动了本地的既有发行包），不实测就动手等于拿门禁换猜测，
  故列为任务组 C。
- **把仓库改公开**：公开仓库的 Actions 分钟数不计量，这是最彻底的解法，但涉及代码公开，
  属于人类的决策，不由 AI 代拍（同 GitHub Pro：付费决策同理）。
- **什么都不做**：每次推送 7~12 分钟，并行时叠加，且挂死的极端情况没有上限。

## Assumptions

| ID | 假设 | 依赖条件 | 失败影响 | 验证状态 |
|----|------|----------|----------|:--------:|
| A1 | 纯文档变更不可能让 Android 构建变红 | 构建的输入只由源码与构建脚本决定 | 真出问题时门禁漏拦 | 已验证（判定只按路径；代码/构建脚本/CI 配置一律触发构建，四个历史提交样本逐一验过） |
| A2 | 构建缓存能跨轮存活于 GitHub 缓存 | setup-gradle 的 `gradle-home-v1` 缓存覆盖 `caches/build-cache-1` | 只省下同轮内的重复 task，时长基本不降 | 部分验证（本轮 36 次 `FROM-CACHE` 证明构建缓存生效；跨轮存活待下一轮代码变更推送确认，见任务组 B） |
| A3 | 并发取消不会掩盖需要知道的失败 | 取消只作用于非 master/main 的 ref | 中间提交的失败可能不复现 | 已验证（实现后自查发现最初按 ref 聚合会在 master 上互相作废，已改为分支感知；权威分支每轮跑到结论） |
| A4 | 超时上限不会误杀正常 run | 正常 run 不超过 12 分钟 | 正常构建被腰斩 | 已验证（近四轮 7~12 分钟，上限设在 30 分钟，余量充足） |

## 方案评分

| 方案 | 评分 | 说明 |
|------|------|------|
| 并发去重 + 文档变更跳过 + 构建缓存 + 超时上限（采纳） | 5/5 | 四项各治一段成本，且都不削弱门禁：代码变更照旧全量构建，job 仍上报成功 |
| 只加并发去重 | 2/5 | 只治并行，连续推送的文档轮次照旧全量重跑 |
| 删掉 master push 触发，只留 PR 门禁 | 3/5 | 省得最彻底，但 master 失去独立验证，push 场景的 lifecycle-audit 一并丢失 |
| 把仓库改公开（分钟数不计量） | 4/5 | 效果最好，但属代码公开决策，须人类定夺 |
| 不治理 | 0/5 | 每轮 7~12 分钟，并行叠加，且没有挂死上限 |
