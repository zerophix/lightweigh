# DEC-058: Room v8 对齐已签库表目标态

> 把 Notion 已签 DEC-S01…S16（无 S06）落成下一次 Room 版本，不另做 MVP 裁剪。

---

## 决策

人类已于 2026-10-23 签下 Notion「DEC-库表目标态默认」的推荐默认。本仓以 **AppDatabase version 8** 一次迁移承接，不改 1~7 的 schema 快照。

权威页：

- [DOC-库表设计](https://app.notion.com/p/40241bd50f8a810398d3ee3473f9485b)
- [DEC-库表目标态默认](https://app.notion.com/p/40241bd50f8a815cb61af4a592a15f40)

| 签条 | 本仓落点 |
|------|----------|
| DEC-S01 | `measurements` 重建：PK `recordId`（存量用 SQL UUIDv4）、`updatedAt`（迁入时等于 `measuredAt`）、`deletedAt`、`syncStatus`、`note`；`UNIQUE(memberId, measuredAt)`。水位与冲突看 `updatedAt`。`measuredAt` 仍是采样时刻。推送冲突键改为 `owner_id,record_id`。 |
| DEC-S02 | 新表 `goals`，`memberId` 主键。进程打开时从 `scalehub_goals` 导入；之后 Room 为读权威，不再回写 SP。`calorie`/`water` 仍走 profiles。`targetWeight` **不**放进云 payload（未知列会使整份档案 upsert 失败）。 |
| DEC-S03 | `health_logs` 继续同步。习惯不进 UI Must；只补 Entity `@Index(memberId)`，与 6→7 已创建的 `index_habits_memberId` 对齐并进入导出 schema。 |
| DEC-S04 | 新表 `members`。表空时从 `scalehub_members` JSON 导入，写入仍镜像 JSON 一版。无家庭云、无邀请字段。 |
| DEC-S05 / S11 | 注销成功后清本机测量库、档案、目标、头像、缓存、`unit_prefs`，成员重置为「我」，再 `signOut`。清本机走同一套本地擦除，**不**调用云，**保留** session（PH-R4）。两处都保留 `scalehub_consent`。删成员仍只删头像文件，测量/日志/习惯与档案键留下（列表按 memberId 不可见；文案「本机保留」只描述删成员）。 |
| DEC-S07 | `ConsentStore` / SP `scalehub_consent`：`privacyPolicyVersion`、`userAgreementVersion`、`consentedAt`。已进入且无版本键时写入 `legacy`。本 PR 无再同意 UI。 |
| DEC-S08 / S09 | `ProfileStore` 为档案与单位权威。`MemberStore` 绑定后档案/单位 API 委托 ProfileStore，并一次性导入旧键。`unit_prefs` 仅在档案单位键不存在时迁一次。删成员不清档案键。 |
| DEC-S10 | `HabitPo` `@Index("memberId")` 与 Migration、8.json 一致。 |
| DEC-S13 / S14 / S15 | 测量与健康日志软删写 `deletedAt`（epoch ms UTC），列表查询滤掉墓碑，同步读口包含墓碑。新时间列用 epoch ms UTC。解绑写 `devices.unboundAt`，不删设备行、不删历史测量；`devices.updatedAt` 默认 0。`boundAt` 仍是 TEXT（云 `bound_at` 是日期串）。活跃列表滤 `unboundAt IS NULL`；`allDevices()` 含已解绑且 `active=false`。 |
| DEC-S16 | `measurements.syncStatus`：0 干净 / 1 待推 / 2 冲突。另建 `pending_sync` 给 profile、devices、goals 做入队与成功后清除。没有独立重试调度器。`sync_status` 不上云。 |
| health_logs PK | `(memberId, loggedAt, type)`，并加 `updatedAt`、`deletedAt`。 |

目标与成员的 SP 不在 SQLite 里，**不**写进 `MIGRATION_7_8`，由 Store 首次打开导入。

### 云端跟进（本 PR 不能改云表）

客户端已按目标态组 payload。云表缺列时 upsert / 带 `updated_at` 的增量拉取会失败，水位不推进（失败关闭，不双请求）。

云侧待加：

- `measurements`：`record_id`，唯一 `(owner_id, record_id)`，`updated_at`，`deleted_at`，`note`
- `health_logs`：`updated_at`，`deleted_at`（冲突键仍是 `owner_id,logged_at,type`）
- `devices.unbound_at`（可选；当前只把解绑行推成 `active=false`）
- `profiles` / goals：`target_weight`（当前只打本地日志）

`bound_at` 与本地 `boundAt` TEXT 的类型统一另列，不在本迁移里改列类型。

家庭云与邀请不在本 PR。

## Assumptions

| ID | 假设 | 依赖条件 | 失败影响 | 验证状态 |
|----|------|----------|----------|:--------:|
| A1 | 旧测量 PK 是全局 `measuredAt`，故 `UNIQUE(memberId, measuredAt)` 对存量成立 | schema 1~7 | 迁移在重复采样时刻上失败 | 由 7→8 数据保留测试覆盖 |
| A2 | 云表尚无 `record_id` / `updated_at` | 后端 DDL | 测量与健康日志推送、以及水位>0 的拉取失败关闭 | 单测锁冲突键；真云待 DDL |
| A3 | `target_weight` 不能塞进现有 profiles upsert | 云列未知即整单失败 | 目标体重只留本机 | 代码路径不写该列 |
| A4 | 无模拟器时连接测试不在本机会话执行 | MigrationTestHelper | v7→v8 只在 CI/真机跑 | 静态对拍 + 本机 sqlite3 演练 |

## 方案评分

| 方案 | 评分 | 说明 |
|------|------|------|
| 一次 7→8（采纳） | 5/5 | 签条是同一目标态，拆多版只会让在途用户多走几步空迁移 |
| 按 DEC-S 拆成多版 | 2/5 | PK 重建无法拆开，中间版没有可独立发布的语义 |
