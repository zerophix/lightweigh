# DEC-038: 称重链路缺陷修复（P0 假断开 + 死重试按钮 + P1 连点重复落库）

> 全链路审查（ScaleRoute → MeasureSession → SessionPhase → AndroidBleLink → 协议层）发现
> 2 个必现级 P0 缺陷与 3 个 P1 缺陷；本 DEC 记录修复取舍。P0-1/P0-2 连锁构成
> 「连上却测不了」的死屏：假「连接已断开」+ 按钮无响应。

---

## 决策

### P0-1 电量读取失败误报「连接已断开」（组 A）

**根因**：`AndroidBleLink.read()` 在特征缺失/GATT 读失败时复用 `onIndicateFailure`
（订阅失败语义通道），而 `MeasureSession.onIndicateFailure` 对 `linkReady` 态一律
`scheduleDisconnectPrompt()`——电量是协议**可选**特征（PDF 表 3.3），无电量特征的秤
订阅成功后 700ms 必弹假断开。

**修法（两层防御）**：
1. `BlePort` 新增 `onReadFailure(reason: String)` 回调（默认调 `onCharacteristicRead`
   不改既有实现），`AndroidBleLink.read()` 失败改走该通道——读失败与订阅失败分离。
2. `MeasureSession` 新增 `onReadFailure`：只 `_state.update { notice = reason }`，
   不触发断开提示/重试。
3. 兜底：`onIndicateFailure` 进入 `scheduleDisconnectPrompt` 前先查
   `ble.isConnected()`，链路存活则降级为 notice（防其他误报路径）。

### P0-2 「重新连接」死按钮（组 B）

**根因**：`showReconnectPrompt()` 只改 UI state 不改 phase，phase 停在
`Linked(linkReady=true)`；而 `retryConnect()` 首行守卫 `phase.linkReady → return`。
按钮恰好只在该状态出现 → 永远无效。触发场景：秤休眠自动断连（常见）或 P0-1 假断开。

**修法**：`showReconnectPrompt()` 将 phase 经 `SessionEvent.Downgrade` 降为
`Linking(picked=true)`（保留 mac/binding，`suppressNextDisconnect=false`）。
`retryConnect()` 守卫不变——降级后 `linkReady=false` 自然放行，走既有
`ble.connect(currentMac, ..., connectionMode())` 路径。纯函数转移可单测。

**为何不选**：在 `retryConnect` 里对 `linkReady` 分支先 `ble.disconnect()` 再重连——
多一次链路 teardown，且 disconnect 回调会再次进入 `onDisConnected` 产生二次状态迁移，
复杂度高于相位降级。

### P1-3 确认保存连点重复落库（组 C）

**根因**：`confirmSave()` 守卫在 `scope.launch` 之前，双击 = 两个 `finishSave` 排队；
`finishSave` 只判 `sealedResult != null` 不判 `result.saved`。主键 `measuredAt` 毫秒
时间戳两次盖章不同 → 两条记录。旧库「20 秒内重复测量覆盖上一条」规则未移植。

**修法（本轮）**：`finishSave` 开头加 `if (sealed.saved) return`（ConsumeConfirm 后
二次进入直接退出）。20 秒覆盖去重属数据语义变更，留待与 P1-5/G5 一起裁定。

### 真机复测追因（2026-10-21 追加）

真机反馈「能连接但唤醒后停在等待态」的两轮日志取证结论：

1. **链路两处「固件静默即死锁」点已兜底**：订阅链只由 `onDescriptorWrite` 推进、写队列只由 `onCharacteristicWrite` 推进，固件不回调即整链冻结（时间/用户信息发不出，秤不启动体成分测量）。各加 3s 超时（订阅跳过继续推进、写入按失败推进），迟到回调靠 `pendingDescriptor` 身份校验忽略。
2. **扫描日志穷举结论：0 条秤广播**。两段日志共 47 条广播，对照协议标记（表 3.1 `FF F0`、表 2.1 `10 FF C0`）程序化检查命中 0 条，`[session]` 侧 `device picked`/`connect` 从未出现——链路停在触发事件（秤广播）缺失处，非状态机断跳。按协议 3.1「当蓝牙未连接时通过广播包获取体重信息」，秤处于被连接状态即停止广播；占线方排查（本 App 未释放连接 / 第三方 App / 仅 bonded 不算）由 `onDeviceFound` 两守卫的去重证据日志判定（`scan gate: ... already connected` / `... not bound`）。对齐参考项目唯一扫描链路差异：`SCAN_MODE_BALANCED` → `SCAN_MODE_LOW_LATENCY`（参考 BLEManager.kt:86，半占空比会整段错过唤醒短促广播）。
