# DEC-039: 蓝牙调试悬浮球与 2 万行日志缓冲

> 真机联调需要看到连接全过程与每一帧蓝牙收发；以 App 内悬浮球面板呈现内存环形缓冲，仅 debug 构建生效。

---

## 决策

1. **日志缓冲 `BleDebugLog`（application 层 object，纯 JVM）**：`ArrayDeque` 环形缓冲，上限 `MAX_LINES = 20_000` 行（超出丢最旧），`synchronized` 全程一把锁（BLE binder 线程写、主线程读）；行格式 `HH:mm:ss.SSS [tag] message`。不引入 android.Log（application 层纯 JVM 守卫）。
2. **双写策略**：`AndroidBleLink.blog()` = `Log.d("BLE_DEBUG", …)` + `BleDebugLog.add("ble", …)`——logcat 行为不变，悬浮面板共享同一数据源。原 11 处单行 + 1 处多行 `Log.d("BLE_DEBUG")` 全部收敛到 blog()。
3. **插桩范围**：AndroidBleLink 补齐传输层日志——TX（queued/write/ack/fail，含 hex）、RX（notify/read，含 hex）、订阅逐特征进度（cccd/skip/ack/done）、服务发现 dump、读失败分支（原先静默）；MeasureSession 补齐编排层日志 25 处——设备选定/协议重绑/广播投递/连接四回调/订阅回调/下发 writeTime+sendUser/帧解析结果（含 parse=null 丢弃）/封存/落库（含拒绝与跳过分支）。
4. **UI `DebugOverlay`（app `ui.debug` 包）**：App 内悬浮球（48dp、可拖动、松手吸附左右边缘），点击展开全屏面板——LazyColumn 滚动 + 一键复制（Clipboard，异常捕获提示）+ 清空 + 跟随底部（上滑暂停、回底恢复）；数据面板打开期间 400ms 轮询 snapshot()。`BuildConfig.DEBUG` 门控（app 模块 buildFeatures 开 `buildConfig = true`），release 构建无悬浮球。挂载点 MainActivity `Box { MainShell(); DebugOverlay() }`（覆盖登录门前的场景）。

## Assumptions

| ID | 假设 | 依赖条件 | 失败影响 | 验证状态 |
|----|------|----------|----------|:--------:|
| A1 | 连接与测量过程都发生在 App 前台，无需系统级悬浮窗 | 用户不切出 App 观察日志 | 切出后看不到实时日志（可回来看，缓冲不丢） | 已验证 |
| A2 | 2 万行字符串常驻内存可接受（约 2-4MB） | 单次会话时长有限 | 极端长会话增加 GC 压力 | 已验证 |
| A3 | 400ms 轮询对调试观察足够实时 | 秤数据帧率约 1-2Hz | 面板比 logcat 略滞后一帧 | 已验证 |

## 方案评分

| 方案 | 评分 | 说明 |
|------|------|------|
| App 内悬浮球 + 内存环形缓冲（采纳） | 5/5 | 零权限、ArchUnit 现有守卫直接覆盖（ui 只依赖 application）、连接过程全在 App 内、实现最小 |
| 系统级悬浮窗（SYSTEM_ALERT_WINDOW） | 2/5 | 需授权流程（MIUI 额外坑）、需 Service + Window 管理、跨 App 观察收益在本场景很小 |
| 仅转发 logcat（面板读 logcat） | 1/5 | 读 logcat 需 READ_LOGS 权限（App 自身可读自己的，但 API 限制多）、格式解析脆弱、无法一键复制整理后的内容 |
