# DEC-068: 批次合并队列 —— 把"每分支全量验证"换成"批次单次验证"

> 实测：6 个分支各自冷构建 5~10 分钟，光等待就吞掉整个交付周期；
> 而分支之间 90% 的冲突来自共享状态（已由 DEC-064/067 消除）。
> 真正的风险在"合并后的组合"，不在孤立分支。

## 决策

### 1. 队列模型

```
候选分支 = origin/master + 合并所有候选分支（--no-ff）
验证一次（local-ci，车道 auto/full）
通过 → git push origin HEAD:master（一次推送）
     → 关闭对应 PR、删除分支与 worktree、回填任务板、主干快检
失败 → 保留候选供排查，不推送
```

### 2. 为什么是"批次验证"而不是"每分支验证"

| 维度 | 每分支验证 | 批次验证（采纳） |
|---|---|---|
| 冷构建次数 | N 次 | 1 次 |
| 集成风险 | 未覆盖（各自绿不等于合并绿） | 直接覆盖 |
| 冲突处理 | 每次合并都要解 | 一次解决，冲突即指名分支 |
| 失败定位 | 分支内 | 候选上可二分（`--keep` 保留现场） |

### 3. 与既有机制的关系

- 任务级质量：`gov-task-done`（文件/原型/verify_commands）——不进队列前先过
- 批次质量：本队列的一次 local-ci
- 主干质量：`gov-post-merge-check`（可选，按需全量）
- 单一写者：队列是唯一写共享状态与 master 的自动化（DEC-064）

### 4. 失败语义

- 合并冲突 → 指名冲突分支，中止本次（已完成的分支不推）
- 验证失败 → 不推送，候选保留（默认清理，`--keep` 保留）
- 推送失败 → 明确报错，master 不变

## Assumptions

| ID | 假设 | 失败影响 | 验证状态 |
|----|------|----------|:--------:|
| A1 | 候选分支之间文件不重叠（认领锁 + target_files 保证） | 冲突增多，仍可定位 | 观察中 |
| A2 | 一次全量验证足以代表批次质量 | 漏检组合问题 | 已验证：批次内一次 full build + 全测试 |
| A3 | 直接 push master 可接受（无 CI 时代） | 绕过 PR 记录 | PR 保留并在合入时关闭，附 commit |

## 来源: 2026-10-24 交付周期被"N 次冷构建"拖垮的实测复盘
