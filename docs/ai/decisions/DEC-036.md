# DEC-036: M2 前置硬缺口闭环（水位线/对账/幂等/多成员隔离/全链路测试/AppContainer 端口化/文档对齐）

> 基于 20261021_m2-prereq-checklist 核验结果，完成 F-001~F-006 六项硬缺口，为 M2 业务逻辑开发扫清障碍。

---

## 决策

### T-010: SyncService 水位线/对账/幂等（F-001，Critical）

**问题**：`SyncService` 无水位线/对账/幂等机制——同步重启无法增量，只能全量；进程死/网络断后下次启动无对账依据；无幂等键验证。

**方案 A（采纳）**：新增 `sync_state` 表，复合主键 `(tableName, memberId)`，每表每成员独立水位线。
- `pushedWatermark`：本机已成功推送到云端的最大时间戳（measurements 是 measuredAt，health_logs 是 logged_at）
- `pulledWatermark`：云端已成功拉回本机的最大时间戳
- **先推后记**：`upsert` 返回 `true` 才更新水位线（失败时 watermark 不变，下次可重推）
- `between(watermark + 1, MAX)`：`between` 是 inclusive on from，`+1` 排除已推的行
- 幂等性由 PostgREST `on_conflict=merge-duplicates` 兜底，本地水位线只是优化闸门

**方案 B（否决）**：在 `MeasureRecord` 加 `syncedAt` 字段，逐行标记。缺点：表结构侵入性强，删除/修改记录时难以维护。

**实施**：
- `SyncStatePo`（Room Entity）+ `SyncStateDao` + `SyncStatePort`（application 端口）+ `RoomSyncStateRepository`（infra 实现）
- `AppDatabase` v5→v6 迁移：`CREATE TABLE sync_state (tableName TEXT, memberId TEXT, pushedWatermark INTEGER, pulledWatermark INTEGER, updatedAt INTEGER, PRIMARY KEY(tableName, memberId))`
- `SyncService` 注入 `SyncStatePort?`（可为 null 以兼容旧路径）

### T-011: 多成员同步隔离测试（F-002，Critical）

**问题**：`SyncServiceTest` 14 个测试无一覆盖成员切换场景，用户 A→B 切换可能数据串污染。

**方案 A（采纳）**：新增 4 个测试：
- `用户切换后旧成员数据不被新用户上传`：验证 watermark 按 (tableName, memberId) 隔离
- `拉取时云端多成员数据按cloud_member_id正确归属`：验证 `memberId()` 传递链
- `MemberScopeChanged事件后全量重查但不重复推云`：验证事件过滤
- `多成员推送_cloud行带正确owner_id`：验证 `session.subject(token)` 作为 `owner_id`

### T-012: 全链路端到端测试（F-003，Critical）

**问题**：「本地写→DataChange→SyncOnLocalWrites→SyncTrigger→SyncService→CloudDataPort→云端确认」全链路无自动化验证，靠人工点点。

**方案 A（采纳）**：新增 `FullChainSyncTest`，7 个场景：
1. 正常链路：本地写入→事件→订阅点火→SyncService.push→CloudDataPort.upsert
2. 事件类型过滤：非 LOCAL_WRITES 事件不触发推送
3. 游客门：非正式账号 no-op
4. 失败重试：upsert 失败后 watermark 不更新，下次可重推
5. 幂等：重复推送无新行时不再 upsert
6. 增量推送：只推新行
7. 多事件合并：Mutex 串行合并，最终 watermark 是最大时间戳

**坑**：`SharedFlow` 无活跃订阅者时发射即丢弃——`SyncOnLocalWrites.start()` 启动的 `collect` 协程在 `runTest` 中不会立即执行，测试中必须先 `advanceUntilIdle()` 等订阅者挂载再发事件。

### T-014: AppContainer 端口化（F-005，High）

**问题**：`AppContainer` 直接暴露 `ProfileStore`/`RoomDeviceRepository`/`AndroidBleLink` 等 infra 具体类型，表现层可绕过端口调用非端口方法。

**方案 A（采纳）**：新增 ArchUnit 负例 `appcontainer公开属性不得暴露infra具体类型`，检查所有 public getter 返回类型不在 infrastructure 包。同时将 `cloudGateway`/`memberRepository`/`goalStore`/`database` 改为 `private`（仅容器内部使用）。

**坑**：Kotlin 的 `private val x: Foo` 会生成 `private final Foo getX()`，ArchUnit 的 `methods` 包含私有方法，必须过滤 `!modifiers.contains(PRIVATE)`。

**问题**：`STATUS.md`/`README.md`/`02_Architecture.md` 仍描述 M1（云同步未接入），与代码脱节。

**方案 A（采纳）**：更新文档反映 M2 同步已实现：
- `02_Architecture.md`：系统上下文图、模块职责表、ArchUnit 规则数（6→14）

## 方案评分

| 方案 | 评分 | 说明 |
|------|------|------|
| 水位线表 + 先推后记（采纳） | 5/5 | 崩溃可重推但不丢；复合主键天然支持多成员；`between+1` 正确排除已推 |
| syncedAt 逐行标记（否决） | 2/5 | 表结构侵入性强；删除/修改难维护；需改 3 个 Entity |
| 全量推送 + 云端去重（否决） | 3/5 | 无本地水位线，每次全量推；网络浪费；云端去重逻辑复杂 |
