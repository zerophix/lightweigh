# DEC-022: 移植重构开发计划与落实保障机制 —— 启动健康记录纵切

> 从旧库 qk-health-android 完整移植并升级到 v2 DDD 框架的总计划与"严格按框架落地"的
> 机械保障；本 DEC 同时承载首切片 A（健康记录纵切）的执行任务组。

---

## 决策

### 一、落实保障机制（回答"如何保证代码严格按脚手架框架"）

每条计划项绑定**介质 + 检测时机 + 可执行验证**，无一条靠自觉（治理五问：时机/介质/可验证/盲点/自测差距）：

| 保障项 | 介质 | 时机 | 可执行验证 | 已知盲点 |
|---|---|---|---|---|
| 分层不被破坏 | 编译器守护（domain/application 纯 JVM 无 android.jar）+ ArchUnit 规则 | 提交时测试执行 | 守卫负例测试（违规夹具必红，已入库） | 无——机械强制 |
| UI 零业务、无全局总线 | ArchUnit UI 守卫 + 屏幕四件套三关评审 | M4 首切片上锁（T-006） | 规则负例（随 T-006 建立） | **上锁前为立约期**，靠 DEC-021 约定+评审兜底 |
| 源码变更必带 DEC+DevNotes | pre-commit + CI lifecycle-audit（不可绕过） | 提交瞬间 | 本次会话已多次被钩子实际拦截 | --no-verify 可绕过 pre-commit，CI 不可绕 |
| 移植行为不失真 | 每条旧库规则配行为测试（黄金对照），语义变更必须另立 DEC | 每切片测试执行 | 测试失败即红（GOV-TEST-005 并入 validate） | 旧库自身 bug 的"忠实性"需人工裁决（本切片 weight 委托即一例） |
| 不越放行门槛 | G1-G5（DEC-020）+ README 交付状态表 | 里程碑收尾 | 零信任评审终审（已在案） | G5 真机对拍依赖硬件窗口 |
| 多 session 不污染 | 路径级暂存集审计（每次提交输出清单） | 每次提交 | commit 记录内审计清单 | T-003 门禁未启用（待人类），文件内夹带需 diff 审查 |
| 计划不漂移 | 任务组状态在 DEC-022 front-matter + 任务板接力 | 每切片收尾 | wf-task-board / GOV-PROTO-003 僵尸任务检测 | 依赖人类确认 next_action |

### 二、移植总计划（阶段化，依赖排序）

| 阶段 | 内容 | 载体 | 前置 |
|---|---|---|---|

### 三、移植忠实性三原则

1. **产品规则事实源是旧库《需求文档》**，不是旧库代码——代码与需求冲突时按需求裁决并记 DEC。
2. **规则迁移必带行为测试**：从 UI 抢救的规则（趋势筛选、8 类记录校验）在 application/domain 层
   逐条钉住；测试注释标注旧库出处（文件:行号）。
3. **语义升级显式声明**：如 weight 类型在旧库写入测量表而非健康记录表（MeasureActivity 同源路径），
   本切片以构造守卫拒绝 type="weight" 入健康记录并注释出处——忠实于行为，不忠实于表象。
