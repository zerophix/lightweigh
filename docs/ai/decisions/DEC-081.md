# DEC-081: UI 接入波 —— 呈现式屏接入 DDD 数据流

> 2026-10-27 实测：`docs/notes/NOTE-20261027-001.md` 盘点出约 20 个呈现式屏已交付但**零 DDD 数据流**——用 `remember { mutableStateOf(...) }` 持本地演示状态，副作用回调是空实现，代码注释自述「本轮只完成状态推进」「不假装已接数据层」。

---

## 背景与问题

### 现状（代码证据）

| 项 | 数值 |
|---|---|
| 已完整接入 DDD 的屏 | ~14 个（测量/趋势/习惯/我的/历史/报告/记录/设置/认证/设备/成员/AI问答，走 UDF 四件套） |
| 纯呈现式、零 DDD 的屏 | ~21 个（A 档 21 可导航但演示数据 + B 档 4 死代码） |
| 已装配待接线的 DDD 能力 | 15+ 端口/用例（`AppContainer` 全暴露，**全部有真实实现**） |

### 核心矛盾

**DDD 层能力是现成的，但没接到呈现式屏上。** 具体表现为三类：

1. **副作用空回调**：`onRenameSaved`、`onSubmitFeedback`、`onExport`、`onGeneratePlan` 等回调是空实现，注释自述「真实提交在调用方」「不落库」。
2. **演示状态**：屏内 `remember { mutableStateOf(...) }` 持本地演示 UiState，非 ViewModel 数据流。
3. **死代码**：`AiCards`/`MeasureHelp`/`AccountLifecycle`/`HealthConnectPlatform` 无 Route 或宿主引用。

### 与 DEC-078 的边界

DEC-078 做**领域逻辑下沉**（application 计算 → domain service），解决"domain 贫血"。本 DEC 做**UI 接入**（呈现式屏 → ViewModel → application/domain 用例），解决"功能不可达"。二者互补、不冲突：

```
DEC-078: application ──下沉──► domain/service   （domain 贫血 → 充血）
DEC-081: app 呈现式 ──接入──► ViewModel ──► application/domain   （功能不可达 → 可达）
```

---

## 决策

### 核心原则

1. **呈现式屏不重建**：已交付的 Screen 是好的，保留静态文案与逐字原型对齐；接入发生在 Route/ViewModel/数据层。
2. **优先复用既有能力**：`AppContainer` 已暴露 15+ 端口/用例，接入**优先接线**，其次才补缺失能力（Batch 2）。
3. **诚实标注**：接不动的能力（如真实固件 OTA）标注「待外部依赖」，不伪造数据源（延续 DEC-061 先例）。
4. **按批推进**：Batch 1 纯接线 → Batch 2 补能力 → Batch 3 复用复杂能力 → Batch 4 死代码裁决。

### 接入范式（UDF 四件套补齐）

对每个缺口屏，把 `remember { mutableStateOf(...) }` 替换为：

```
Route( 创建 ViewModel) ──► ViewModel(factory = 注入 AppContainer 用例)
                              │ 状态 StateFlow
                              ▼
Screen(纯渲染，state + onIntent)   ← 呈现式组件不改
```

### 明确不动的

- 不重建已交付的呈现式 Screen（保留原型文案匹配）
- 不改 `Qk*` 设计系统组件
- 不伪造数据源（真实能力缺失时用「空回调 + 诚实注释」而非假数据）

---

## 方案评分

| 方案 | 评分 | 说明 |
|---|---|---|
| **A：分批接入 DDD 数据流（采纳）** | 5/5 | 功能可达、复用既有能力、每批独立验收、风险递进可控 |
| B：一次性全接入 | 2/5 | 21 屏同批改动大、验证面失控、易互相冲突 |
| C：只接核心屏、其余留演示 | 3/5 | 缓解最痛路径，但功能不可达未根治 |
