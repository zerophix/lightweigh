# DEC-021: UI 层架构约定 —— UDF + 屏幕四件套 + 读模型下沉

> 旧库 qk-health-android 的 UI 因全局刷新总线与千行页面文件不可持续扩展；v2 的 M4 界面开发
> 以本决策立约，先于任何页面代码生效。

---

## 决策

对 M4（完整页面）确立五条 UI 架构约定：

1. **分层铁律：UI 零业务**。趋势筛选、月度汇总、差值计算、AI 摘要的业务上下文一律在
   :application 查询/用例层；Composable 只渲染 UiState，ViewModel 只调应用服务。
   以 ArchUnit 守卫机械强制（app 的 ui 包禁 import infrastructure 与存储/云 SDK），
   规则随 M4 首个垂直切片落地（DEC-021 task A）。
2. **单向数据流（UDF）替代全局刷新总线**。每屏一个不可变 UiState（StateFlow 暴露），
   动作为 sealed Event，一次性效果（导航/Toast/权限弹窗）走独立 Effect 通道。
   跨屏刷新由数据源层信号的订阅关系决定——禁止复刻旧库 UiRefresh 全局 version 计数。
3. **屏幕四件套按 feature 目录组织**：`<Name>Screen.kt`（无状态可预览）、
   `<Name>ViewModel.kt`、`<Name>UiState.kt`（State/Event/Effect）、`<Name>Route.kt`。
   新增页面 = 新增目录 + 路由表一行，零改动现有页面。
4. **读路径下沉读模型**：application 查询服务按 UiState 形状直出读模型
   （沿用 MeasurementQuery 方向），筛选/聚合在服务层可黄金测试，ViewModel 只做转发与格式化。
5. **设计系统先行于页面**：色彩/字号/间距 token 与 5-8 个基础组件先立，
   页面只声明使用，禁止页面内散落硬编码样式。

配套约定：M4 按垂直切片交付（一次一个页面四件套，过预览+ViewModel 测试+架构守卫三关），
禁止旧库式 big-bang；导航为类型安全 Route，需求文档信息架构即导航图规格，
"报告→去完善→返回仍在报告"等返回语义写成导航测试。

## Assumptions

| ID | 假设 | 依赖条件 | 失败影响 | 验证状态 |
|----|------|----------|----------|:--------:|
| A1 | 手工 AppContainer 装配在页面超过 10 个前仍够用 | 组合根保持唯一装配点 | 装配散落，需迁 Hilt（另立 DEC） |  待验证 |
| A2 | 读模型按 UiState 形状直出不会造成 application 对展示层的知识泄漏 | 读模型只含数据形状不含文案样式 | 若泄漏则改为 domain 出聚合、UiModel 映射 |  待验证 |
| A3 | navigation-compose 类型安全路由满足返回栈语义需求 | 官方库版本能力 | 若不够（如面板/路由区分），引入 kotlinx-serialization 路由方案 |  待验证 |

## 方案评分

| 方案 | 评分 | 说明 |
|------|------|------|
| UDF+四件套+读模型下沉（采纳） | 5/5 | 与既有 MeasureViewModel 种子同构；新增页面与规则变更的改动面最小且可机械守护 |
| 照搬旧库页面直连 Store 模式 | 1/5 | UiRefresh 总线与千行 Pages.kt 正是本次拆解确认的不可扩展病根 |
| 全套 MVI 框架（第三方 orbit/mavericks 等） | 3/5 | 能力等价但引入新依赖与学习成本，当前规模收益不抵成本；预留升级路径 |
