# DEC-034: DDD 架构合规性修正——领域事件总线、语义耦合下沉与仓储契约诚实化

> 来源：`docs/ai/reviews/20261020_ddd-architecture/opencode__20261020_143000.md`（10 项 finding）。
> 本次逐项核验后，确认 8 项属实、1 项数字有误（F-006 说三处实际两处）、1 项不成立（F-010）。

## 决策

### 先说评审报告本身的问题

评审报告的统计口径没跟上二轮核验的降级：front-matter 与统计表都写 `critical: 2`，
但 F-002 已在二轮核验中降为 Medium——理由成立（`SyncTrigger` 的 fire-and-forget 是
P0 产品决策「写在本机即上云，恢复只作兜底」的显式实现，见该文件类注释，非架构泄漏）。
降级后真实分布为 **Critical 1 / High 3 / Medium 4 / Low 2**，`reviews/index.md` 的
「2 Critical」一并更正。

**F-010 撤回**。报告称「`application/trigger/ble` 放的是 BLE 回调适配器，本质是基础设施
适配器，应移到 `infrastructure/ble`」，但核验结果是：

| 报告所述 | 实际 |
|---|---|
| `application/trigger/ble/` 存放 BLE 回调适配器 | 该目录**不存在**（`application` 下无 `trigger` 包） |
| 应实现 `domain` 定义的 `BleGateway` 端口 | `domain` 中**无 `BleGateway`**，端口是 `application/ble/BlePort` |
| 建议移到 `infrastructure/ble` | BLE 实现**已经在** `infrastructure/ble/`（`AndroidBleLink`、`BlePermission`） |

结论：`ArchitectureTest.kt:18` 的注释「trigger 为 BLE 回调/后台任务**预留落点**」与守卫规则里
8 处 `com.xcwk.scalehub.trigger..` 白名单，被当成了已存在的代码。它建议的落点恰是现状。
保留白名单作为预留位无害，故不作为修正项；若将来确要启用，另立决策。

### 任务组划分依据

10 项 finding 不是十件独立的事，按**耦合关系**归成七组，避免同一处代码被改多轮：

- **A（事件驱动一条线）**：F-001 与 F-002 共用同一个解。`DataRefreshBus` 下沉 domain 并
  抽出 `DomainEventBus` 端口后，`SyncTrigger` 自然可以由基础设施侧订阅事件触发，
  用例不再注入同步策略。分两次做等于把同一批 service 改两遍。
- **B（语义耦合，低成本先做）**：F-004 是唯一能被**静态扫描**钉死的语义违规
  （`RoomDeviceRepository` import `domain.algorithm`），修复半天，且能立刻固化成治理规则
  防回归——报告附件也正是这么建议的。
- **C（领域模型行为）**：F-003 的工厂方法与 F-006 的 Clock 是同一件事的两面——
  创建编排收进聚合根工厂后，时间戳也应由工厂内的 Clock 盖章，用例不再取时间。
- **D（仓储契约）**：F-005 采用**方案 B（最小改动）**而非报告推荐的方案 A。理由：
  方案 A 要把 `memberId + measuredAt` 改成复合主键，牵动 Room 实体、DAO、查询与
  数据库设计 v3 三处同步；而本项目的多成员维在仓储层是**有意决策**（多处注释已声明），
  真正的问题只是「不变量没在接口签名上显式化」。方案 B 让接口诚实，成本三分之一。
- **E / F（精简与值对象）**：工作量大且不阻塞 M2，排 P2。
- **G（报告修正）**：报告自身的错误若不修，下一个人读到「2 Critical」会误判紧急度，
  读到 F-010 会去搬一个不存在的目录。

### 依赖与顺序

```
A（事件总线）──→ C（工厂方法可借 Clock）
B（语义耦合）──  独立，成本最低，优先落地并固化治理
D（仓储契约）──  独立
E / F            排 P2
G                与代码无关，先行
```

B 优先于 A 落地：它半天见效、能立刻被 `gov-code-check` 钉死，而 A 要动三个 service
与 domain 事件模型，是本 DEC 里唯一有设计不确定性的部分（事件粒度、订阅时机）。

### 任务组 B（2026-10-20，已完成）

F-004 的实际情况比报告描述更严重：报告只指出 `RoomDeviceRepository` 反向耦合，
实际是**同一条「协议→默认算法」规则散落三处**：

| 位置 | 语义 | 写法 |
|---|---|---|
| `RoomDeviceRepository.kt:36` | 绑定时取默认算法 | `if (OkokBia.uses(p)) OkokBia.ID else ALGORITHM_BUILTIN_1` |
| `MeasureSession.kt:222` | 测量时按协议覆盖 | `if (OkokBia.uses(p)) OkokBia.ID else device.algorithmId` |
| `MeasureSessionTest.kt:104` | 测试假仓储复制一份 | 同第一处 |

这正是 F-003「业务规则散落在用例、不可复用」的一个具体实例——只是评审没把它和 F-004 关联起来。
三处的回退值各不相同（绑定默认 / 历史记录），故收敛为一个带回退参数的领域方法：

```java
// ScaleDevice.java
public static String algorithmFor(String protocolId, String fallback) {
    return OkokBia.uses(protocolId) ? OkokBia.ID : fallback;
}
```

三处分别传 `ALGORITHM_BUILTIN_1`、`device.algorithmId`、`ALGORITHM_BUILTIN_1`，语义不变。
`infrastructure` 从此不认识 `domain.algorithm`。

依赖了**实现细节**而非端口），静态 import 扫描是唯一可行面。负例已验：造违规文件退出码 1、

### 任务组 D（2026-10-20，已完成）

核验后发现实际情况比 F-005 描述的更彻底：`MeasureRecord.memberId` 不只是"默认空串
允许无效态"，而是**一个从未持有过有效值的死字段**：

| 路径 | 现状 |
|---|---|
| 写入 `RoomMeasurementRepository.save` | `toPo()` 先写 `memberId = ""`，再 `.copy(memberId = memberId())` 用当前成员覆盖——聚合的值被丢弃 |
| 读取 `toDomain()` | 压根不传 memberId，构造器默认 `""` |
| 云端还原 `SyncService.mergeMeasurements` | 用 9 参构造器（不含 memberId）→ `""` |
| 全项目读 `record.memberId` | **零处** |

即：字段声明了、构造器接收了、然后没人读它。多成员隔离这条核心约束既不在接口签名上，
也不在聚合里，只藏在仓储实现的一行 `.copy()` 中。

**落地形态（方案 B）**：

```kotlin
interface MeasurementRepository {
    suspend fun save(record: MeasureRecord, memberId: String)   // 归属成为必答问题
}
```

- `MeasureRecord` / `HealthLog` **删除** memberId 字段（连同 10 参构造器）
- 两个 Room 实现的 `save` 用参数写 PO，**读取仍按当前成员过滤**——查询是「我看到了什么」，
  不是「谁写了什么」，两者语义本就不同
- 用例与 `SyncService` 各注入 `memberId: () -> String`，容器统一接 `activeMemberId`
- `InMemory*` 实现记录 `savedMemberIds` 供断言

**为什么不用方案 A（复合主键）**：它要把 `memberId + measuredAt` 改成主键，牵动 Room 实体、
DAO、查询与数据库设计 v3 四处同步；而本项目的多成员维在仓储层是**有意决策**（多处注释
已声明），真正的问题只是"不变量没在接口签名上显式化"。方案 B 以三分之一成本达到同效。

**新增 2 个测试**：`save 的归属参数原样到达实现`（接口→实现的传递性）、
`save 写入的 memberId 进 PO`（Room 映射层）。

### 任务组 E（2026-10-20，评估后部分不采纳）

这一组的两条处方都经核验后**不予采纳**，理由是它们建立在与代码事实不符的前提上。
记录在此，避免后人以为是漏做。

**F-008（仓储接口含 between/recent）——处方在本架构下无法执行。**
评审建议「区间查询迁往 `application.query`，由查询服务直接访问 DAO/数据库视图」。
但 `application` 不得依赖 `infrastructure`（ArchUnit 强制，且 `application.query` 现无任何
infrastructure import）。要执行只有两条路：改守卫允许内层反向依赖外层（架构倒退），
或在 `domain` 再定义一套查询端口、由 infrastructure 实现——那等于把同一个 Room 类
拆成两个接口名，读写语义的分离靠命名而非结构，收益是文字上的整齐。

`between/recent` 的 15 处调用里，14 处位于 `application.query`（本就是评审认可的查询层）
与 `SyncService`（全量读取用于推送与合并去重），只有一处越界：

```kotlin
// ScaleViewModel:67 表现层直捅仓储，绕过查询服务
app.container.measurementRepository.recent(1)
```

已改为 `app.container.measurementQuery.recent(1)`，与其余读路径同口径。**这一处才是真问题。**

**F-009（MemberRepository 混合业务行为）——诊断与事实不符。**
评审称「`Member` 实体无行为（贫血）；仓储替换时业务逻辑随之丢失」。实际 `Member` 已有
三个工厂方法（`nextId` / `nextSlot` / `normalizeNickname`）与 `MAX = 8` 常量，
`MemberStore.add()` 只是编排：


### A 组方案偏离评审原案（2026-10-20 评估后决定）

评审 F-001 的处方是「`DataRefreshBus` 下沉 `domain`、`application` 仅依赖接口、
`infrastructure` 提供实现」。评估后**不予采纳**，三条理由：

1. **会污染纯模型层**。`domain` 当前零协程依赖（grep 其中的 `Event` 全是协议帧
   `ScaleEvent`，与领域事件无关），也没有任何 domain 代码需要发事件。评审的论据是
   「**若** domain 要发事件则不得不反向依赖 application」——这是对未来可能性的设计，
   为尚不存在的需求给纯模型层引入 `kotlinx.coroutines`，本末倒置。
2. **抽象背后没有平台差异**。`DataRefreshBus` 的实现就是一个 `MutableSharedFlow<Unit>`
   包装，零平台能力。接口 + infrastructure 实现只会多一层无收益的间接；
   六边形架构要求抽象服务于**可替换的实现差异**，此处不存在。
3. **会让表现层依赖领域层的总线概念**。订阅方是 4 个 ViewModel（表现层），若总线接口在
   `domain`，表现层就得依赖领域层的基础设施概念。ArchUnit 不拦（`app → domain` 合法），
   但语义上是倒退。

**真实缺陷另有其二**（评审未指出）：

- **事件无类型**：`RecordMeasurement` / `DeleteMeasurement` / `RecordHealthLog` /
  `ProfileUpdated` / `RestoreCompleted` 发的都是同一个 `Unit` 信号，订阅方收到后无差别
  全量 `refresh()`——用户改个头像，趋势页也要重查测量数据。
- **发布点越层**：`SettingsViewModel.restore()` / `deleteAccount()` 直接
  `refreshBus.notifyChanged()`，表现层在发数据变更信号。

故 A 组改为：**保持 `DataRefreshBus` 在 application（应用层编排关注点，位置本就正确），
事件类型化 + 发布点归位 + 用例剥离 `SyncTrigger`**。F-002 因此顺带解决，且比评审的
「短期过渡：调用方决定是否触发」更彻底——同步触发完全由容器在事件流上挂订阅，
用例既不知道刷新也不知道同步。
