# DEC-027: 云同步上传断链修复（P0）与导航口径对齐

## 决策

1. **P0：云同步「只下拉不上传」断链修复**。全项目审计发现 `SyncService.push()` 完整实装、
   注入容器、六项单测全绿，但生产代码零调用——本地写的一切（新测量/健康记录/档案变更）
   永不上云，「恢复账号」只拉取登录时的旧快照，换机迁移拿到过期数据。
   **修复口径**：新增 `SyncTrigger`（fire-and-forget：`scope.launch { runCatching { push() } }`），
   挂到三个写用例的成功出口（`RecordMeasurementService` / `RecordHealthLogService` /
   `UpdateProfileService`）。要点：
   - 网络绝不上本地写入的关键路径——写用例不等推送结果，失败自吞，UI 无感；
   - 游客天然 no-op（push 首行 `isFormalAccount` 即挡），测试侧用记录型 lambda 注入，
     不需要假 SyncService（生产侧 `SyncTrigger(applicationScope) { syncService.push() }`）；
   - 删除用例不点火（既有语义：日常同步只上传不删除云端多出行，注销才删云端）；
   - 「恢复账号」降级为兜底路径，不再承担唯一的上云入口。
2. **导航口径对齐**（并行会话遗留批次，全量测试取证后采纳，无新决策）：
   称重未绑定态按钮从「返回」改为直达设备页绑定（`SelectTab` 同时清覆盖栈）；
   首页历史入口从切趋势页改为推历史覆盖页（对齐旧库 QingkeApp.kt:339 与「我的」页口径）。

## Assumptions

- push 是全量快照 upsert（幂等、含 profile/devices/measurements/health_logs 四表），
  连续触发按序执行而非折叠是 SyncService 已声明的语义，本批不改动；
- 应用级 `CoroutineScope(SupervisorJob() + Dispatchers.IO)` 随进程存活足够承载
  fire-and-forget（无 WorkManager，按事件触发即可，不做周期同步）；
- 登录后是否自动 restore 合并属产品决策，不在本批范围（保持设置页手动恢复）。

## 方案评分

| 方案 | 判定 |
|---|---|
| 写用例内联 push（阻塞等网络） | 15s 连接超时 × 5 表，写操作会被网络拖死 |
| VM 层各写各的触发 | 「VM 忘记调」正是本次事故的根因，触发点必须收拢在写用例 |
| SyncTrigger + 写用例点火（采用） | 单一点火收口、失败隔离、测试用 lambda 注入零假件 |
