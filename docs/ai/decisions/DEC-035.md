# DEC-035: 组合根只暴露端口类型

> 表现层经 AppContainer 取到的是 infrastructure 具体类型，而 ArchUnit 追不到这条路径；
> 改为容器私有具体实例、对外只暴露端口，用编译期而非守卫堵住它。

---

## 决策

**采纳方案 A**：`AppContainer` 四个暴露具体类型的属性（`bleLink: AndroidBleLink`、
`deviceRepository: RoomDeviceRepository`、`profileStore: ProfileStore`、
`sessionStore: SessionStore`）改为私有 `XxxImpl`，对外只给端口类型：

| 对外属性 | 类型 | 来源 |
|---|---|---|
| `blePort` | `BlePort` | `AndroidBleLink` |
| `deviceRepository` | `DeviceRepository` | `RoomDeviceRepository` |
| `profileReader` / `profileWriter` | `MemberProfileReader` / `MemberProfileWriter` | 同一个 `ProfileStore` |
| `authPort` / `cloudSessionPort` | `AuthPort` / `CloudSessionPort` | 同一个 `SessionStore` |

容器内部装配一律引用私有 `XxxImpl`（具体类型可向上转型为任意端口，编译必然通过）。

### 为什么不是加守卫（方案 B）

评审原建议是给 `ArchitectureTest` 加一条规则。实测证明这条路线在这个盲区上**无效**——
ArchUnit 的 `directDependenciesFromSelf` 不追踪方法体内的调用返回类型。探针结果：

```
invokevirtual AppContainer.getBleLink:()Lcom/xcwk/scalehub/infrastructure/ble/AndroidBleLink;
```

字节码明确引用了 `AndroidBleLink`，而 ArchUnit 对 `ScaleViewModel` 统计出的 106 个直接
依赖里，`infrastructure` 包的类**一个都没有**。在这种追踪能力下，任何基于
`dependOnClassesThat` 的规则都看不见这条路径。

## Assumptions

| ID | 假设 | 依赖条件 | 失败影响 | 验证状态 |
|----|------|----------|----------|:--------:|
| A1 | 表现层只需要这四个属性的端口能力，不需要具体类的非端口方法 | Factory 只做构造参数传递 | 若某处需要具体方法，该处会编译失败并暴露 | 已验证 |
| A2 | 容器内部装配全部可以改引私有 Impl 而不影响行为 | 服务构造参数本就声明为端口类型 | 同上，编译期即暴露 | 已验证 |

## 方案评分

| 方案 | 评分 | 说明 |
|------|------|------|
| 方案 A：容器只暴露端口（采纳） | 5/5 | 编译期保证，不依赖守卫的追踪能力；表现层代码本就声明为端口参数，改动只在容器属性与 6 处取值 |
| 方案 B：ArchUnit 加返回类型规则 | 1/5 | 实测证明 ArchUnit 追不到方法体内的调用返回类型，规则会静默放行——比没有规则更危险 |
