# DEC-031: KSP 钉到公开仓库存在的 2.3.9（修复 CI 插件解析失败）

> catalog 钉的 KSP 2.3.2 在任何公开仓库都不存在，只活在本机 Gradle 缓存里，于是本地恒绿、CI 恒红。

---

## 决策

PR #1 的 `build-and-guard` 在解析插件阶段失败，报 `Plugin [id: 'com.google.devtools.ksp', version: '2.3.2'] was not found`，
并列出六个源（阿里云 google / gradle-plugin / public、google()、mavenCentral()、gradlePluginPortal()）全部未命中；
重跑结果相同，排除偶发。同一 run 的 `docs-validate` 与 `lifecycle-audit` 均为成功——故障被限定在 Gradle 插件解析这一层。

根因是**依赖版本的可获取性**，不是网络：

- 查 Maven Central 公开索引（该 artifact 共 136 个版本）：KSP 的 2.3.x 一线只有 `2.3.7`、`2.3.8`、`2.3.9`，
  **没有 2.3.2**；旧编号方案止于 `2.2.0-2.0.2`。
- 本机 `~/.gradle/caches/modules-2/files-2.1/com.google.devtools.ksp/com.google.devtools.ksp.gradle.plugin/2.3.2/<sha>/com.google.devtools.ksp.gradle.plugin-2.3.2.pom`
  **有实物**（`symbol-processing-gradle-plugin/2.3.2` 同样在）。Gradle 的规则是「缓存命中则不问仓库」，所以本地永远绿；
  CI 是干净环境，只能逐源去问，于是六源全 404。日志里零网络报错、整体一分钟快失败，正是这一特征。

采纳的修法是把版本钉到一个**公开存在**的版本：

- **采纳：`ksp` 由 `2.3.2` 改为 `2.3.9`**（公开索引里的最新版）。改动落在 `gradle/libs.versions.toml` 一行。
- **否决：保留 2.3.2，改仓库顺序或加镜像**。版本本身不存在于任何仓库，换顺序、加源都不可能找到它。
- **否决：保留 2.3.2，继续靠本机缓存开发**。CI 会一直红，门禁形同虚设；这正是本次事故被拖到推送才暴露的原因。
- **备选（未采纳）：钉到 2.3.7 / 2.3.8**。同样公开存在，但不是最新；留作 2.3.9 与 Kotlin 2.2.10 不兼容时的回退。

### 执行结果

- **版本层（完成）**：`gradle/libs.versions.toml` 的 `ksp = "2.3.2"` 改为 `"2.3.9"`。`infrastructure` 经
  `alias(libs.plugins.ksp)` 与 `ksp(libs.room.compiler)` 使用它，Room 的 `_Impl` 实现类由 KSP 生成
  （`AppDatabase_Impl`、`DeviceDao_Impl`、`HealthLogDao_Impl`、`MeasurementDao_Impl`，debug 与 release 各一份）。
- **本地验证（完成）**：为避免重蹈「缓存自证」的覆辙，先 `./gradlew --stop` 停掉 daemon，再把
  `com.google.devtools.ksp.gradle.plugin/2.3.9` 与 `symbol-processing-gradle-plugin/2.3.9` 从缓存移走，
  然后跑 `./gradlew build assembleAndroidTest`：`BUILD SUCCESSFUL in 2m24s`，254 个任务中 247 个真实执行
  （非 up-to-date），编译 + 单测 + lint + APK + androidTest 源集编译全过。
- **待验证（组 B）**：版本可获取性最终由 GitHub runner 判定——推送后 PR #1 的 `build-and-guard` 若转绿，
  即证实 `2.3.9` 在公开仓库可解析。
- **如实记录的疑点**：定位期间一次「全新 `GRADLE_USER_HOME`」实验曾意外通过，与「2.3.2 不存在」相矛盾，
  怀疑由热 daemon 复用或本机网络中间层缓存造成，未定论。本次修法不依赖该实验，故未继续追查。
