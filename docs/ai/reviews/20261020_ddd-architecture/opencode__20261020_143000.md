## 发现列表

### F-001 | Critical | DataRefreshBus 放在 application 层 —— 领域事件总线错层 【硬约束】

**位置：** `application/src/main/kotlin/com/xcwk/scalehub/application/DataRefreshBus.kt`

**描述：** `DataRefreshBus` 是领域事件总线（写用例发事件、查询用例订阅），语义属于领域层基础设施抽象，但被放在了 `application` 模块。

**根因：** 早期将"跨屏刷新信号"视为应用层编排工具，未识别为领域事件基础设施。

**影响：**
- `domain` 层若要发事件（如算法计算完成、设备绑定完成）不得不反向依赖 `application`，或把发射逻辑硬塞进用例（现状：`RecordMeasurementService` 直接 `refreshBus?.notifyChanged()`）
- 破坏 `domain ← application` 单向依赖的语义完整性
- 阻塞 M2 云同步的事件驱动架构：同步本应订阅领域事件，现只能耦合用例

**修复建议：**
1. 移到 `domain.types` 或新建 `domain.event` 包
2. 定义 `DomainEventBus` 接口（`publish(event)` / `subscribe(eventType)`）
3. `infrastructure` 提供实现（复用现有 `SharedFlow`），`application` 仅依赖接口
4. 用例改为发布领域事件（如 `MeasurementRecorded`），不再直接触发刷新/同步

**验收标准：** `ArchitectureTest.domain不依赖任何外层与AndroidSDK` 继续通过；`application` 不再包含 `DataRefreshBus`；`infrastructure` 有实现类。

**核验记录 (2026-10-20 二轮)：**  确认属实。`find application -name DataRefreshBus.kt` 存在；`grep -rn 'DataRefreshBus' application/src/main/kotlin/com/xcwk/scalehub/application/service/` 三个 service 均直接依赖。ArchUnit 规则未捕获（编译方向合规），但语义向外层倾。

**修复记录 (2026-10-20，DEC-034 组 A)：**  已处理，但**未采用本条的修复建议**。
经评估，「下沉 domain + infrastructure 提供实现」会为尚不存在的需求给纯模型层引入
协程依赖、多一层无收益的间接、并让表现层依赖领域层的总线概念（详见 DEC-034
「A 组方案偏离评审原案」）。真实缺陷另有其二并已修：事件由 `Unit` 改为 `DataChange`
sealed 类型（订阅方按需订阅，不再全量重查）；`SettingsViewModel` 的发布动作下沉到
`RestoreAccountService` / `DeleteAccountService`（表现层不再发数据变更信号）。

### F-002 | High → Medium(降级) | SyncTrigger 注入写用例 —— 可选的事件解耦改进点 【软约束】

**位置：** `application/src/main/kotlin/com/xcwk/scalehub/application/service/RecordMeasurementService.kt:18`、`RecordHealthLogService.kt:18`、`UpdateProfileService.kt:15`

**描述：** 写用例构造器注入 `SyncTrigger?`，执行成功后直接 `syncTrigger?.fire()`。

**根因：** 将"本地写完即触发云同步"视为业务规则硬编码在用例中。

**影响：**
- 用例单测必须 mock 基础设施（`SyncTrigger` 属于 `application.sync`，实质是基础设施策略）
- 换同步策略（批量/定时/手动/仅 Wi-Fi）要改用例代码，违反单一职责
- 同步失败处理、重试、幂等性逻辑污染业务用例
- 违反"用例只编排领域逻辑"原则

**修复建议：**
1. 用例返回聚合根（`MeasureRecord`/`HealthLog`/`MemberProfile`）
2. 引入领域事件（配合 F-001）：用例发 `MeasurementRecorded` / `HealthLogRecorded` / `ProfileUpdated`
3. `infrastructure` 侧事件处理器订阅并触发 `SyncService`，策略完全在基础设施层可配
4. 或短期过渡：调用方决定是否触发同步（ViewModel/trigger 层），用例不再注入 `SyncTrigger`

**验收标准：** 所有写用例构造器移除 `SyncTrigger` 参数；用例内无 `syncTrigger?.fire()`；同步由事件处理器或调用方触发。

**核验记录 (2026-10-20 二轮)：**  **降级修正**。`SyncTrigger.kt` 类注释明确记录：「P0 断链修复：写在本机即上云，恢复只作兜底」「fire-and-forget，不阻塞写入，异常吞掉」。这是**产品级决策 (P0)** 的显式实现，非架构泄漏。两种方案均满足需求：现有方案（用例直触发）更直接；事件解耦方案（F-001 配合）测试更纯、策略更灵活。改为 **Medium(可选改进)**，不阻塞 M2。

**修复记录 (2026-10-20，DEC-034 组 A)：**  已按 F-001 配合方案完成，比本条建议的
「短期过渡」更彻底——三个写用例已完全移除 `SyncTrigger` 注入，只发 `DataChange`；
点火由新增的 `SyncOnLocalWrites` 在事件流上订阅 `LOCAL_WRITES` 触发。
订阅侧单独成类是为了可测（藏在容器里只能靠集成测试，而容器依赖 Android Context）。
「写在本机即上云」的 P0 语义未变，且新增 GOV-CODE-005 防回归
（`application.service` 不得 import `application.sync`）。

### F-003 | High | MeasureRecord / HealthLog / MemberProfile 为贫血模型 —— 核心创建编排仍在用例 【软约束】

**位置：** `domain/src/main/java/com/xcwk/scalehub/domain/model/MeasureRecord.java`、同目录 `HealthLog.java`、`MemberProfile.kt`

**描述：** 领域对象已含构造器守卫、类型校验、工厂方法、状态转换（见核验记录），但**创建时序编排**（算法选择 + 时间戳盖章 + 档案快照拼装）仍沾在 `RecordMeasurementService` 等用例中。

**根因：** 事务脚本思维迁移到 DDD 分层，把过程式逻辑留在了应用服务，领域对象虽拥有 invariants 但缺「统一创建入口」。

**影响：**
- 业务规则散落在用例，不可复用（如"如何从原始输入创建测量记录"只能在用例里写一次）
- 用例膨胀，测试必须走完整用例路径，无法单测领域逻辑
- 新增创建路径（如导入历史数据、云端恢复）易漏规则、不一致

**修复建议：**
给每个聚合根添加**工厂方法/静态创建方法**，封装创建逻辑：

```java
// MeasureRecord.java
public static MeasureRecord create(MeasurementInput input, MemberProfile profile, String mac, String algoId, Clock clock) {
    double fat = input.hasImpedance() 
        ? Algorithms.of(algoId).fatPercent(profile.male(), profile.ageYears(), profile.heightCm(), input.weightKg(), input.impedanceOhm())
        : input.manualFat().orElse(FAT_NOT_CALCULATED);
    return new MeasureRecord(clock.now(), input.weightKg(), input.impedanceOhm(), fat, mac, algoId, profile.snapshot());
}
```

用例简化为：`repository.save(MeasureRecord.create(cmd, profile, clock))`

**验收标准：** 所有写用例不再包含算法选择、时间戳、快照拼装逻辑；领域对象单测覆盖创建规则。

**核验记录 (2026-10-20 二轮)：**  **修正**。实体类已含行为：
- `Member`：`nextId/nextSlot/normalizeNickname` 工厂逻辑
- `HealthLog`：`init` 不变式 + `HealthLogType` 类型合法化
- `MemberProfile`：`ageYears()` 计算 + 构造守卫
- `ScaleDevice`：`withActive()` 状态转换
故非「全无行为」，而是「创建编排缺统一入口」。保留 High，但修正描述。

**修复记录 (2026-10-20，DEC-034 组 C)：**  已完成。三个聚合根各补统一创建入口：
`MeasureRecord.create`（体脂计算编排 + 时间盖章）、`HealthLog.create`（习惯主值归一）、
`MemberProfile.create`（昵称 trim+截断）。`RecordMeasurementService.execute` 从 20 行
降到 8 行，只做「取档案 → 落库 → 广播」。直接构造器保留给 Room 行映射与云端还原——
那些场景时间戳来自数据本身，重新盖章反而错。

### F-004 | High | RoomDeviceRepository.bind() 引用领域算法 —— 基础设施层语义耦合领域知识 【硬约束】

**位置：** `infrastructure/src/main/kotlin/com/xcwk/scalehub/infrastructure/persistent/repository/RoomDeviceRepository.kt:58-59`

```kotlin
import com.xcwk.scalehub.domain.algorithm.OkokBia
val algorithm = if (OkokBia.uses(protocol)) OkokBia.ID else ScaleDevice.ALGORITHM_BUILTIN_1
```

**描述：** 仓储实现里直接调用 `domain.algorithm.OkokBia` 判断协议对应的默认算法。

**根因：** "协议→默认算法"的映射规则被当作持久化细节处理。

**影响：**
- 换算法/增协议要改仓储代码
- 仓储单测必须 mock 领域算法，破坏基础设施层测试隔离
- 语义耦合反向：`infrastructure` 依赖 `domain` 的**实现细节**而非端口

**修复建议：**
把映射规则下沉到领域：
- `ScaleDevice` 增加工厂方法 `ScaleDevice.bind(name, mac, protocolId)` 返回带默认算法的实体
- 或领域服务 `DeviceBindingService.determineAlgorithm(protocolId)`
- 仓储只存传入的 `algorithmId`

**验收标准：** `RoomDeviceRepository` 不再 import `domain.algorithm.*`；算法映射规则在 `domain` 单测覆盖。

**核验记录 (2026-10-20 二轮)：**  确认属实。`grep -n 'OkokBia' infrastructure/src/main/kotlin/com/xcwk/scalehub/infrastructure/persistent/repository/RoomDeviceRepository.kt` 命中第 3 行 import 与第 36 行调用。ArchUnit 未捕获（同包依赖），但语义耦合反向。

**修复记录 (2026-10-20，DEC-034 组 B)：**  已完成。实际情况比本条描述更严重——同一条
「协议→默认算法」规则散落三处（`RoomDeviceRepository` 绑定取默认、`MeasureSession`
测量时覆盖、测试假仓储抄一份），三处回退值还不一致。已收敛为
`ScaleDevice.algorithmFor(protocolId, fallback)`，`infrastructure` 从此不认识
`domain.algorithm`。新增 **GOV-CODE-004** 防回归（静态扫描 infrastructure 的 import，
ArchUnit 抓不到这类「方向合法但依赖了实现细节」的问题）。

### F-005 | High | 仓储接口撒谎 —— memberId 隐式注入导致领域模型允许无效态

**位置：** 
- `domain/src/main/kotlin/com/xcwk/scalehub/domain/repository/MeasurementRepository.kt`（接口无 `memberId`）
- `infrastructure/src/main/kotlin/com/xcwk/scalehub/infrastructure/persistent/repository/RoomMeasurementRepository.kt:28`（实现强行塞 `memberId`）

**描述：** `MeasurementRepository.save(MeasureRecord)` 签名不含 `memberId`，但实现里 `record.toPo().copy(memberId = memberId())` 强行注入。`MeasureRecord.memberId` 默认空串，**领域模型允许无成员归属的测量记录**。

**根因：** 多成员隔离被视为应用策略，未上升为领域模型的复合主键一部分。

**影响：**
- 接口契约与实现不符，阅读接口无法知晓"成员隔离"这一核心约束
- `MeasureRecord` 可处于"无成员"无效状态，编译器不报错
- 仓储实现耦合 `memberId: () -> String` 供应器，测试、替换实现困难

**修复建议（两选一，推荐方案 A）：**
- **方案 A（正统 DDD）**：`MeasureRecord` 主键 = `MemberId + MeasurementTime` 复合值对象，仓储接口按复合键存取，多成员隔离成领域不变量
- **方案 B（最小改动）**：仓储接口显式加 `memberId` 参数：`save(memberId: MemberId, record: MeasureRecord)`，`MeasureRecord` 移除 `memberId` 字段

**验收标准：** 仓储接口签名与实现语义一致；`MeasureRecord` 无法构造为无成员状态；ArchUnit 继续通过。

**核验记录 (2026-10-20 二轮)：**  **修正**。项目注释多处承认「多成员维在仓储层」为有意设计决策。接口未显式暴露 `memberId` 导致契约与实现语义不符，`MeasureRecord.memberId` 默认空串允许无效态。这不属于「撒谎」（有意设计），但属于**不变量未显式化**。保留 High，修正描述为「接口隐藏成员归属不变量」。

**修复记录 (2026-10-20，DEC-034 组 D)：**  已按方案 B 完成。三轮核验发现比本条更彻底：
该字段**从未持有过有效值**——写入被仓储 `.copy(当前成员)` 覆盖、读取压根不传、
全项目零读点，是个声明了却没人读的死字段。现 `save(record, memberId)` 让归属成为
接口签名上的必答问题，聚合删除该字段；读取仍按当前成员过滤（查询是「我看到了什么」，
不是「谁写了什么」）。未采用本条推荐的方案 A（复合主键），理由见 DEC-034 组 D：
它要牵动 Room 实体、DAO、查询与数据库设计 v3 四处，而真正的问题只是不变量未显式化。

### F-006 | Medium | 时间戳盖章分散在各写用例 —— 领域规则未收敛

**位置：** `RecordMeasurementService.kt:45`、`RecordHealthLogService.kt:33`、`UpdateProfileService.kt`（无时间戳但同理）

**描述：** "时间戳由用例盖章、存储层不盖章"是领域规则（PRD 明确），但分散在每个写用例的 `System.currentTimeMillis()` 调用中。

**根因：** 缺乏 `Clock` 抽象，规则靠自觉而非类型系统保证。

**影响：** 新增写用例易忘记、或用 `Instant.now()`/`System.nanoTime()` 不一致；测试时难以控制时间（需 mock 静态方法）。

**修复建议：**
1. `domain.types` 引入 `Clock` 接口：`fun now(): Long`（毫秒）
2. `application` 注入 `Clock`（生产用 `SystemClock`，测试用 `FixedClock`）
3. 聚合根工厂方法内部用 `clock.now()`，用例不可直接取时间

**验收标准：** 无写用例直接调用 `System.currentTimeMillis()`；时间相关单测使用 `FixedClock` 确定性验证。

**核验记录 (2026-10-20 二轮)：**  确认属实。`grep -rn 'System.currentTimeMillis()' application/src/main/kotlin/com/xcwk/scalehub/application/service/` 三个 service 各一次。无 `Clock` 抽象。

**核验记录 (2026-10-20 三轮修正)：**  **数字更正**。复跑同一命令实际命中 **2 处**（`RecordMeasurementService.kt:42`、`RecordHealthLogService.kt:30`），`UpdateProfileService` 中并无该调用。结论方向不变（无 `Clock` 抽象、时间戳规则未收敛），但「三个 service 各一次」的表述不准确。

**修复记录 (2026-10-20，DEC-034 组 C)：**  已完成。新增 `domain/types/Clock`
（`SystemClock` / `FixedClock`），时间由聚合根工厂内部取——用例拿不到时钟即无法绕过
盖章规则。写用例中的 `System.currentTimeMillis()` 已清零（验收标准达成）。

**范围界定（比本条原建议更收敛）**：项目里另有 4 处 `currentTimeMillis`——协议时间包
下发（`TimePacket`）、查询侧算「今天」（`HomeGoalQuery`）、token 过期（`SessionStore`）、
日期选择器初值（`HistoryScreen`）。这些是**不同语义**，本条原表述「无写用例直接调用」
本就只约束写入路径，故未一并抽象。边界已写进 `Clock` 的文档注释，防止后人误扩大理解。

### F-007 | Medium | 缺少值对象 —— 原始类型泛滥导致类型安全缺失

**位置：** 全项目

| 概念 | 现状 | 缺失值对象 |
|---|---|---|
| MAC 地址 | `String` + `MacFormat.normalize()` | `MacAddress` |
| 算法编号 | `String` + `Algorithms.of()` | `AlgorithmId` |
| 体脂率 | `Double`，-1 哨兵 | `BodyFatPercent` |
| 时间戳 | `Long` 毫秒 | `MeasurementTime` / `LoggedAt` |
| 成员 ID | `String` UUID | `MemberId` |

**影响：** 参数顺序错、把 `memberId` 传成 `mac`、毫秒传成秒，编译器全不报错，运行时才炸。

**修复建议：** 渐进式引入值对象（每类半天），优先 `MemberId` 和 `AlgorithmId`（跨层传递最频繁）。

**验收标准：** 核心跨层参数全部为值对象类型；无 `String` 直接传递业务标识的公共 API。

### F-008 | Medium | 仓储接口污染查询语义 —— between/recent 属于查询模型不属于仓储

**位置：** `domain/src/main/kotlin/com/xcwk/scalehub/domain/repository/MeasurementRepository.kt`、`HealthLogRepository.kt`

**描述：** 仓储接口包含 `between(fromInc, toExc)`、`recent(limit)` 等报表查询方法。

**根因：** 未区分"聚合根仓储"（按 ID 存取）与"查询模型"（按业务维度读取）。

**影响：**
- 仓储实现被迫实现复杂查询，耦合数据库细节
- `InMemoryMeasurementRepository` 为测试实现了完整查询逻辑，维护成本高
- 领域层接口膨胀，替换存储引擎（如换 ObjectBox）成本大

**修正建议：**
- 仓储接口只保留：`save(aggregate)`、`findById(id)`、`remove(id)`
- 区间查询、最近 N 条、统计聚合 → 迁移到 `application.query` 包（已有 `MeasurementQuery`、`HealthLogQuery`），由查询服务直接访问 DAO/数据库视图

**验收标准：** `domain.repository` 接口仅含存取方法；`application.query` 覆盖所有读取需求。

### F-009 | Low | MemberRepository 接口混合了领域服务与仓储职责

**位置：** `domain/src/main/kotlin/com/xcwk/scalehub/domain/repository/MemberRepository.kt`

**描述：** 接口包含 `add(nickname)`、`switch(id)`、`rename(id, nickname)`、`remove(id)`、`activeSlot()` 等业务行为方法，不止存取。

**根因：** 将"成员管理业务逻辑"塞进仓储接口，而非领域模型 `Member` 聚合根。

**影响：** `Member` 实体无行为（贫血）；仓储替换时业务逻辑随之丢失。

**修正建议：**
- `Member` 增加 `rename()`、`deactivate()` 等业务方法
- 仓储接口仅：`findById`、`findAll`、`save`、`remove`
- `add/switch/activeSlot` 归入领域服务 `MemberManagementService` 或应用服务

**验收标准：** `MemberRepository` 接口精简为标准仓储签名；`Member` 实体含业务行为。
