# 需求到编码链路

> 并发任务的验收锚点。产品行为以上层文档为准，下层只实现已钉住的那一版。DEC-057。

视觉从原型进入实现，原型必须来自产品文档，库表在写界面之前由产品字段驱动。只看任务标题的并发会话会对不齐。每张任务引用具体上层产物，并把上层验收抄进自己的完成定义；上层改了，下层跟着该引用走。

---

## 1. 层级与权威

自上而下。上一层决定「做什么」，下一层只决定「怎么落地」。

| 顺序 | 层 | 决定什么 | 权威位置 |
|------|----|----------|----------|
| 1 | 产品需求 / 产品决策 | 范围、行为、文案句、验收条款 | Notion 空间「轻衡健康」/ `01-产品`：`PRD-产品需求`、模块专文 `PRD-*`、产品决策页 `DEC-*` |
| 2 | 设计 | 已经画完的屏 | Notion `02-设计` 与 Figma；说明页 `DES-*` |
| 3 | 原型 | Figma 未画清的屏与流程 | Notion `03-原型补充-HTML` 的 `UI-*`（入口页标题现为 `03-原型`）。本机工作副本 `design/prototypes/`（gitignore，不入库） |
| 4 | 数据形状 | 表、列、迁移 | `infrastructure/schemas/com.xcwk.scalehub.infrastructure.persistent.AppDatabase/`（当前 `7.json`）与 `AppDatabase` version |
| 5 | 任务与实现 | 本次改哪些文件、如何判定做完 | `.ai/tasks.json` 的 `T-xxx`；屏幕四件套见 [GC-coding-conventions](GC-coding-conventions.md) |

仓库 `docs/ai/lifecycle/01_PRD.md` 只保留工程阶段摘要，不是产品权威。

同一屏上 Figma 与 HTML 冲突：以 Figma 为准，并记产品决策。约定见 Notion「轻衡健康 / 00-规范 / DOC-目录与命名规范」。产品句与代码冲突：行为以已发布 PRD 为准；工程差异另立仓库 `docs/ai/decisions/DEC-xxx.md`，不在任务里改写产品句。

链路总览页使用标题 **DOC-需求到编码链路**（空间「轻衡健康」）。撰写本指南时该标题尚未作为可检索正文出现，引用时只写标题，不要编造 URL。已存在、可按标题检索的入口：`PRD-产品需求`、`DOC-目录与命名规范`、`03-原型`。

没有单独的「数据库设计」Notion 页时，列是否该存在以对应 PRD 的字段句为准，落盘形状以 Room 快照为准。以后若增加数据设计页，任务 pin 写该页标题，不在本指南里预填地址。

## 2. 追溯 ID

任务、PR、会话交接里用这些记号，避免「那个登录页」这种无法复核的说法。

| 记号 | 含义 | 写法 |
|------|------|------|
| M# | `PRD-产品需求` 里的模块号 | `M9` |
| 屏号 | 模块专文里的屏或流 | `A01`、`A02`、`C07` |
| UI-* | HTML 补充原型标题 | `UI-启动引导` |
| 文档 ID | 专文页内冻结号 | `PRD-轻衡-HOME-001` |
| T-xxx | 仓库任务 | `T-045` |
| DEC-xxx | 仓库工程决策 | `DEC-057` |
| Notion `DEC-*` | 产品决策页 | 写全标题。不要当成仓库 `DEC-xxx` 的编号 |

一张就绪任务至少三条引用：PRD（模块或专文，加上屏号或 M#）、schema（快照路径或带理由的不适用）、原型（`UI-*` 或 `design/prototypes/` 下的文件与屏锚点，或带理由的不适用）。

---

## 3. 钉住与冻结

- `acceptance.refs.pin` 写抄录时的文档 ID，加上版本或日期。
- 进行中的任务按 pin 验收。Notion 上出现的新句子不会自动变成这张任务的范围。
- 上层变更打中该 pin：把任务设为 `acceptance.status=blocked`，按新版本重抄 `definition_of_done` 与 `dod_source`，再更新 pin。或者另开 `T-xxx` 只承载增量。
- 同一任务不混用两个 pin。
- 并发任务各自 pin。不共享一句还在改的口头结论。

显式不适用必须带理由，例如 `n/a: 纯领域计算，无屏`。单独的 `n/a` 不算引用。

---

## 4. 级联

上层变了，下层跟着被打中的引用更新，而不是各改各的。

1. PRD 或产品决策变更后，先对照原型。Figma 已有该屏则改 `02-设计` / `DES-*`；没有则改 `UI-*` HTML。缺屏保持「HTML 补全未完成的 Figma」，不用聊天记录补屏。
2. 字段增删：先改 PRD 里的字段句，再改 Room（version+1、Migration、快照入库、仓库 DEC）。不为了让测试通过先加列。
3. 原型里出现 PRD 没有的行为：停工，回到产品文档。AI 不直接改 PRD（约束 FLOW-001）。
4. pin 被打中的未完成任务：更新 pin 与完成定义，或标 `blocked`。已完成任务不回溯改写；增量用新 `T-xxx`。

---

## 5. 自检

开工前按 pin 读上层原文。`definition_of_done` 的每一条都能在 `dod_source` 里找到出处（条款号或原文短句）。做完时用这些条款判断，不用任务标题判断。

机器门禁见 [GC-task-acceptance](GC-task-acceptance.md)：`acceptance.status=ready` 或任务 `in_progress` 时，缺引用即 `GOV-PROTO-005` 失败。`draft` 与已完成历史任务不因此失败，校验只打印警告，避免把现有看板一次打红。
