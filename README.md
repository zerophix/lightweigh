# 轻刻健康 Android（qk-health-v2）

配合 OKOK 协议蓝牙体脂秤使用的个人健康记录 App。记录体重与体成分数据，
本地优先存储，支持后续云端同步与多成员档案。

## 功能现状（M2）

- 手动记录体重（体脂按 builtin-1 公式计算，无阻抗时记为"未计算"）
- 最近测量列表
- 成员档案字段：性别 / 出生年 / 身高（体脂计算输入）
- 健康日志记录（饮食/饮水/运动）
- **云同步（M2 已实现）**：测量记录/健康日志/档案增量推送，水位线/对账/幂等
- **多成员支持**：memberId 显式隔离，水位线按 (tableName, memberId) 复合主键
- 蓝牙称重（M3 规划中，`BlePort` 端口已定义）

## 技术架构

Kotlin + Jetpack Compose + Room + Coroutines，四模块分层，依赖只允许向内：

| 模块 | 类型 | 职责 |
|---|---|---|
| domain | 纯 JVM（零 Android 依赖，编译期强制） | 协议解析、体成分算法、测量模型、仓储端口 |
| application | 纯 JVM | 用例编排（RecordMeasurement：取档案 → 算体脂 → 落库） |
| infrastructure | Android 库 | Room 存储、档案存储、（后续：BLE 网关、云同步） |
| app | Android 应用 | Compose 界面（UDF 单向数据流）、组合根、ArchUnit 架构守卫 |

## 快速开始

```bash
./gradlew build        # 构建 + 全部测试 + 架构守卫
```

- 环境：JDK 17+（推荐 Android Studio 自带 JBR 21）、Android SDK 34
- Android Studio：Open 选择本目录，Gradle JDK 选 embedded jbr-21
- 模拟器：使用 arm64 AVD（如 qk_health_avd）；蓝牙称重需真机
- applicationId：com.xcwk.scalehub

## 协议与算法

体脂秤接入是本项目的核心资产：

- 协议：okok-1（GATT 连接式）、okok-broadcast-1（纯广播）、chipsea-cloud-1（芯海云端版），
  帧解析、分包重组、单位换算均在 domain 层，纯 JVM 可测
- 算法：builtin-1（经验公式）、okok-bia-1（设备回归公式），编号定格历史记录，升级不回算
- 算法正确性由黄金向量测试守护（输入输出向量与跨端契约同源，任何一端漂移即测试失败）

## 路线图

- M2：手机号登录与云端同步（CloudBase，离线保存与上云为两个独立承诺）
- M3：蓝牙称重（三协议接入，连接状态机：显式状态枚举 + 串行写队列 + 断连退避重连）
- M4：完整页面（设备绑定 / 趋势图表 / 体测报告 / 健康日志 / 设置 / 档案编辑）
- M5：8 电极分支算法（分部位阻抗 Z14/Z23 合并与专用系数）

### 反思

- 教训：守卫「能抓什么」必须实测，不能从规则语义反推——我原以为 ArchUnit 的 `directDependenciesFromSelf` 会把方法调用的返回类型算进去（字节码里 `getBleLink:()AndroidBleLink` 的 invokevirtual 明明白白），实测却是一百零六个依赖里 `infrastructure` 一个都没有。若不是顺手写了个探针跑一遍，评审建议的「加一条返回类型规则」会以「守卫已覆盖」的名义被采纳，而它在同一个盲区上会永远放行——规则的存在感反而会掩盖它抓不到东西这件事。
- 教训：防御性重构要先数一数「今天会不会错」，而不是「理论上能不能错」——F-007 主张引入值对象防参数混淆，但它列的三种失效里，两种已被前面的任务组顺带消灭（Clock 收了时间、聚合与 String 混用会编译失败），剩下一种在当前签名下连相邻的同类参数都没有。为不存在的风险预铺类型，代价是十几处调用方改动，收益是零。这类建议的价值取决于「混淆面」是否真实存在，先量再改。
- 教训：评审的「建议」可能从未被本项目的架构约束校验过，采纳前先拿守卫规则验处方、再验诊断——F-008 让查询服务直接访问 DAO，而这条路径恰好是 ArchUnit 明令禁止的（application 不得依赖 infrastructure），照做就得先拆守卫；F-009 断言 Member 实体贫血，可它已有三个工厂方法。验诊断要读实现，验处方只需对一遍约束清单，后者更省事也更常被跳过。
- 教训：拿参考项目做对比前，必须先确认哪一份才是上游——我把 Java 移植版当基准逐行比对蓝牙实现，而真上游是同包名的 Kotlin 版（BLEManager 591 行 vs 805 行），于是 `connectScannedDevice` 整套随机地址连接机制从没进入视野，「芯海秤连不上」的根因也就一直被外围修复掩盖着；直到读到移植方案文档里「保留 connectScannedDevice 逻辑」那一行才对上。基准选错时，后面每一句「逐位一致」都是在跟错的样本比。
- 教训：评审指出真问题，不代表它给的解法也成立——F-001 断言事件总线「错层」应下沉 domain，可 domain 当前零协程依赖、也没有任何代码要在那发事件，照做等于为尚不存在的需求给纯模型层加协程依赖；F-010 描述的目录更是根本不存在（把架构测试注释里的「预留落点」读成了已落地代码）。发现问题的价值归评审，采纳哪条解法仍要自己取证。
- 坑：Kotlin 的尾随逗号带进 Java，报错位置会完全指错方向——参数列表末尾多个逗号，javac 报 `illegal start of expression` 且指向 `);`，一个字都没提逗号；靠数括号逐行排查才定位。跨语言写代码时，语法差异类错误的现场信息基本不可信。
- 教训：治理规则必须能自证，否则会静默空转——gov-code-check 的 ROOT 少算一层父目录，扫到 0 个源码文件却报 PASS；若不是顺手验了一遍，这条规则会一直「绿」着让人以为已被守住。现在它每次运行先拿已知正反例验自己，且扫到 0 文件即失败。
- 教训：并发取消组按分支聚合时，master 上会把上一轮还没跑完的构建作废——而权威分支恰恰要求每一轮都跑到结论。取消只该留给特性分支；否则「刚推一个文档提交」就能悄悄抹掉上一次代码构建的结论，而且表面看一切正常，比红还危险。
- 教训：自己写的机制解释也会错——我在 DEC-033 里断言「gradlew 把 GRADLE_USER_HOME 固定在仓库内，所以构建缓存落点确定」，CI 日志却显示构建缓存在 `/home/runner/.gradle/caches/build-cache-1`，仓库内的 `.gradle-user` 只在本地出现；顺带还查出每轮都在重下 `gradle-9.4.1-all.zip`（`distributionBase=PROJECT` + 目录被 gitignore），白烧约 100 秒。把机制解释写进假设并留验证行，被日志推翻时改文字、不改证据。
- 教训：计量分钟数的 CI 上，「跳过」要落在 step 级而不是 job 级——用 `if` 把整个 `build-and-guard` job 关掉，分支保护上的必填检查会停在「Expected」把合并卡死；正确做法是 job 照跑、只跳过两个重型 Gradle 步骤，并把判定结果与文件清单打进日志，且基线提交不可用（首次/强制推送）时一律按「动了代码」处理——宁可多跑一轮，也不留门禁空洞。
- 教训：一个字段由「谁想写」决定、真正落盘的脚本却另有默认值时，默认值会静默胜出——`ses-session-end.sh` 认真按环境检测身份（还引了 DEC-009「不冒充」），但实际写接力信的是 `wf-inbox.sh`，它把 `from` 硬编码成 claude，于是任何平台的交接信都署 claude，调用方传的身份只进了上下文缓存。同一份身份检测必须在唯一写入口实现（现收口到 `lib-platform.sh` 的 `detect_agent`），否则「检测」只是装饰。
- 教训：等待型命令不要和「有副作用」的命令串在一条链上——把 `git push` 与 `gh run watch` 写在一起时，副作用部分早已完成，整条链却会静默阻塞十几分钟（这次 CI 从 1 分钟快失败变成 11 分钟真构建），使用者既看不到进度也无法判断是卡死还是在跑。收尾命令应当把「动作」与「观察」分离：先拿 run id 回报，再按需查询。
- 教训：多源仓库配置里，「坏源」比「缺源」更致命——阿里云三个镜像对 GitHub runner 返回 502，而 Gradle 的解析遇 5xx 会直接终止（只有 404 才回退下一个仓库），于是排在第一位的镜像在第一次请求就把插件解析判死，后面三个可用的官方源一个都没被问到；日志只留一句「not found in any of the following sources」，看上去像「谁都没有这个包」，实际是「第一个源把门关了」。配镜像时要问的不只是「它有没有这个包」，还有「它从目标网络能否回 2xx」。
- 教训：假设被否证时要立刻换到故障现场取证，不要在本机继续推演——CI 报 KSP `2.3.2` 找不到，本机查公开索引确认该版本不存在，于是断定是「版本问题」；换成公开索引里确实存在的 `2.3.9` 后，CI 报的是**同一个错**（照样列出六源全未命中）。真因在 runner 侧对仓库的解析，不在版本，替换版本只是把故障点原地搬了一次。正确顺序是先拿现场的原始证据（逐源返回码、可达性），再改配置。
- 教训：本地 Gradle 缓存会把「依赖只存在于本机」伪装成一切正常——catalog 钉的 KSP `2.3.2` 在公开索引里查不到（Maven Central 的 2.3.x 一线只有 2.3.7/2.3.8/2.3.9），本机缓存里却有实物，于是本地怎么编都是绿的、看不出任何异常。所以「我这能编过」不构成依赖可用的证据：本地绿与 CI 绿之间隔着缓存这一层，门禁只有跑在干净环境里才算数；判断可获取性要用故障现场或公开索引核对。
- 坑：门禁的检测时机决定它拦在哪一步——R0 的「反思不得复用」在提交时比对 `HEAD`、在干净树上（pre-push / CI）比对 `HEAD~1`，于是任何不刷新反思的提交（比如一条纯 `.gitignore` 的 chore）提交时毫无症状，却会让**下一次推送**直接卡死。等价于隐含要求「每个提交都必须刷新反思」，这条约束不在任何交接说明里，收尾时必然重踩。
- 教训：暂存区不等于「可提交的批次」——并行会话把 featurepage→features 的改名 stage 了、却把调用方的 import 修正留在工作区，暂存快照单独拿出来编不过。分批提交前要问的不是「文件怎么分组」，而是「这一批的完整依赖是否都在批内」：分组按文件、可编译性按编译单元，两者不等价。
- 教训：两个会话共用一个工作树，缺共识的修复会来回反弹——同一条 lint 错误（`java.time` 与 minSdk 冲突）在两会话之间被改红又改绿两次，双方都在「消红」，却没人把「该在构建层脱糖而不是把注解推给调用方」写成文字。结论落进 DEC 才算真的修完，代码层的单方面删改无法收敛。
- 教训：硬编码治理要分「该收口」与「该保留」——URL/域名/网络参数这类单点配置必须收敛（重复硬编码 2 处云域名是隐患，集中到 BackendConfig 后自建后端只改一处）；但尺寸 token 化不能全量铺开，页面里的图标 size/圆角/行内微间距是组件内部尺寸，强 token 化只会让 token 集爆炸且失去语义，保守映射「值恰好等于 token 的页面级间距」才是正解。
- 教训：没有可验证手段的「治理」不做——文案抽取（326 处含动态值占位符）无法写测试证明正确，且项目无多语言需求，强行抽取违背「先写测试再实现」的约束，评估后暂缓，而非为了「完成任务」而做无保护的改动。
- 教训：算法必须与设备电极模式严格匹配——早期实现对 8 电极秤套用四电极公式，数值能产出但口径错配，这类静默偏差比崩溃更危险；现已按模式拆分系数并用黄金向量锁定。
- 坑：本地存储带隐式容量上限等于静默丢数据；v2 用 Room 取代旧存储后该问题从结构上消除，但容量与保留语义必须写进契约。
- 教训：**协议识别不能"按名单选"而要"按能力选"**——`preferAdvertisedProtocol` 原逻辑只对 `okok-broadcast-1`/`chipsea-cloud-1` 才回填广播协议，导致 GATT 设备被误降级为纯广播，表现为"显示已连接却只读广播、无阻抗/体脂"。正确逻辑：识别到的协议若 `requiredCharacteristic() == null`（纯广播），必须保留原设备绑定的 GATT 协议；仅当识别到的协议**有**必选特征时才回填。这类"按能力门控"的修复比枚举协议 ID 更稳健，新协议接入无需改此处。
- 教训：**端口契约测试要"一套用例跑两遍"**——`BlePort` 接口有 FakeBle（单测）与 AndroidBleLink（真机）两套实现，只测 FakeBle 会漏掉真机特有的时序、权限、PHY 协商等问题。T-001 建立契约测试 `BlePortContractTest`，FakeBle 全绿后，同一套用例在模拟器跑 AndroidBleLink（T-017），才能保证语义一致性。单侧测试≠契约验收。
- 教训：**多会话共享暂存区必须显式归属**——`e0d6bcf` 事故：第二会话提交时连带扫入第一会话已暂存的 13 文件，提交信息归因混同。T-003 建立 `ses-claim-staged.sh` 显式声明 + `pre-commit` 归属校验 + `prepare-commit-msg` 自动注入 `Session-Id` footer。核心原则：暂存区文件必须显式声明归属会话；未声明或归属他会话的文件拒绝提交。这将"靠时机不冲突"的隐性约束变为"显式声明+强制校验"的硬约束，彻底消除跨会话误提交。
- 教训：**androidTest 门禁要"先本地跑通再挂 CI"**：`MigrationTest`（v1→v5 全链迁移 + 数据保留）虽早落地，却只挂 `assembleAndroidTest` 编译门禁，**从未在任何门禁上真跑**。T-017 先在本地模拟器跑通 `connectedDebugAndroidTest`（含 v1→v5 迁移 + 数据保留），再在 CI 启用每周定时跑 `connectedAndroidTest`。刻意只挂 `schedule` + `workflow_dispatch`，不挂 `push/PR`——模拟器卡死/超时风险高，仅作定时兜底，不阻塞主干。
- 教训：增量同步的水位线必须「先推后记」——`upsert` 失败时若仍更新 `pushedWatermark`，失败的行会被永久跳过（下次 `between(watermark+1, MAX)` 查不到它们）。正确顺序是：`upsert` 返回 `true` 才更新水位线；`between` 是 inclusive on from，必须用 `watermark + 1` 排除已推的行。幂等性由 PostgREST `on_conflict=merge-duplicates` 兜底，本地水位线只是优化闸门。
- 教训：`SharedFlow` 无活跃订阅者时发射即丢弃——`SyncOnLocalWrites.start()` 启动的 `collect` 协程在 `runTest` 中不会立即执行，若在订阅者就绪前 `notifyChanged`，事件会被静默丢弃。测试中必须先 `advanceUntilIdle()` 等订阅者挂载，再发事件。
- 教训：ArchUnit 检测 `private val` 生成的 getter——Kotlin 的 `private val x: Foo` 会生成 `private final Foo getX()`，ArchUnit 的 `methods` 包含私有方法。检查「公开属性是否暴露 infra 类型」时必须过滤 `!modifiers.contains(PRIVATE)`，否则会误报私有实现细节。
- 教训：批量包名/路径重命名不能依赖 shell 内建替换（转义行为不可控），必须用脚本语言做确定性操作，并在改后做残留复验。
- 教训：拒绝非法数据不等于定义了正确业务规则——每条不变量必须标注来源（契约级/产品级/自设），weight 上限就是产品决策而非厂商契约，混为一谈会让后人误信。
- 坑：测试期望值必须来自独立精算而非印象——单位换算 lb 向量曾手填 69.8，精算为 70.3，当场纠正；这类"期望值笔误"恰是黄金向量机制要防的自身盲区。
- 教训：只存计算结果不存输入的历史无法解释——快照语义必须落到"输入随记录持久化"（schema v2 三列），并用"存档后改档案"测试钉死。
- 教训：空模板事故的根因不是操作失误而是校验盲区——唯一会检查占位符的脚本从未被任何门禁调用，规则写了却不执行等于没写；补规则时又发现按治理笔记的「通用尖括号」思路会误伤合法正文，最终只有用模板 token 白名单并用测试钉住它与模板同步才可靠。
- 坑：去模板化收尾不能只改正文——状态看板的项目名取自 `mkdocs.yml` 的 `site_name`，指标由自动脚本从代码统计生成；不先改源头就重生成，模板身份会立刻「复活」。正确顺序是「先改源头 → 再重生成 → 最后校验」，否则每次收尾都在做无用功。
- 教训：黄金标准（reference/guides 等）不能直接编辑，必须经 `wf-promote.sh` 附一个新 DEC 晋升，正文也不能自带 `## 来源` 行（由晋升脚本写入）；否则来源标注与治理协议对不上，事后审计无法追溯。

- 教训：迁移测试的价值在「链」而不在「步」——单步迁移各自有对拍还不够，v1 老行数据

- 教训：旧库的「占位页」也要如实移植——轻断食/生理期等 21 个入口在旧库就是一句

- 教训：移植前先把旧库读到「能画出全景」——首页全家桶看似吓人，拆开是目标存储+今日汇总
   查询+卡片渲染三件事，而其中两件在落码前就发现旧库 feature 页全是占位文案；
   读源码读到「哪些是真的」之后，工作量估计误差能小一个数量级。
- 教训：多成员这种横切维度，把过滤与盖章放在仓储层是最小爆炸半径——聚合、云契约、

   收口能让下游零感知」，答案往往不是最贴近业务的那一层。
- 坑：三重引号字符串经 shell+python 双层管道已是第二次把 Kotlin 文件结构打碎（这次是
   未闭合的 raw string 吞掉整个类体，报错却在几十行外的 Unresolved）——带转义/三重引号

- 教训：移植解析类代码时，「依赖不可用」是换实现的信号而不是跳过的借口——domain 纯 JVM

   换实现可以，语义漂移不行。
- 坑：Compose 函数签名加了尾随 lambda 参数后，所有旧调用点的 `) {}` 会静默绑定到新参数上而不是原来的——两处预览连报两次才发现是同一个机制；给既有可组合函数追加参数时，尾随调用点要当心 lambda 落位漂移。
- 教训：并行会话的在途文件不是障碍而是资产——面积图三件套在工作区躺了两轮，每轮提交我都用「排除法」把它挡在暂存区外；用户一句「你来做」之后，接管动作是先勘察现状、全量门禁验证、复审后带归属声明入库，而不是按任务清单重写一遍——隔离纪律与接管复用是同一件事的两面。
- 坑：android.net.Uri 是框架类，JVM 单测里连 parse 都是未模拟方法——把「选图结果」在意图里
   降维成 String、Uri 解析下沉到容器 lambda，一次改动同时解开可测性与分层两把锁；
   涉及框架单例/静态的参数传递，先想想测试侧能不能造出来。
- 教训：DatePicker 的 selectedDateMillis 是 UTC 零点而非本地——按日筛选若直接用系统默认时区格式化，东八区早晨八点前的记录会被划错日子；跨时区语义必须显式声明口径（本处固定按 UTC 取日期字符串），否则是又一个「数值能产出但口径错配」的静默偏差。
- 教训：把「白名单」写进守卫测试本身就是最好的 review 卡点——组合根规则上线第一跑就抓出两个生成类（R/ComposableSingletons），放行必须附注释进清单，「新增即改守卫」让豁免永远留在 diff 里；这比在文档里写「组合根只做装配」有效得多。
- 教训：覆盖页用 when 分支替换是隐性状态销毁——下层页面在覆盖页打开时被 dispose，「返回回到刚才页面」在分支式覆盖下天然不成立；改为 Surface 叠放保组合态，导航语义的正确性来自组合结构而非补丁式状态保存。
- 教训：架构守卫的价值在「写代码的当下」兑现——本次 feature 层两处越界（直引 infra 权限类、直触 SharedPreferences）都是 ArchUnit 在同一轮构建里拦下的，修复路径（根包门面 + 容器lambda）比返工便宜一个数量级；分层锁若只在 CI 远端跑，这类「顺手直连」就会沉淀成结构债。
- 教训：转义文本塞进 heredoc+python 双层管道等于把正则交给命运——三重引号字符串经两轮shell 解读后碎成非法 Kotlin，还连带打断了类结构让无关符号一起报 Unresolved；带转义的代码块宁可整段重写（write/edit 工具直投），也不要试图在命令行里精修。
- 坑：把长生命周期的轮换定时器（贴士轮播）直接挂在 runTest 的作用域下，测试收尾会因子协程未结束而悬挂一分钟再报 UncompletedCoroutinesError——测试侧要交给 backgroundScope（结束自动取消），生产侧注入作用域的设计本身就是这次能一行修复的前提。
- 教训：动手移植前先盘点目标仓既有资产——本以为要落码的蓝牙协议层其实早已随命名空间收敛整体移植入库（Java 逐位一致），重复建设会立刻撞 Redeclaration；「先 diff 旧库与目标库再写代码」应成为移植切片的固定第一步，省下的工时远超盘点成本。
- 坑：共享信号总线「无订阅者即丢弃」是设计口径，测试它时必须先 yield 让订阅协程就位，且计数恢复要再推进一次调度器——Main 的 Unconfined 调度器与 runTest 的 Standard 调度器各持一册，「看起来同步」的断言会踩空两回；另批量改宿主接线前先读真实结构（壳层并无历史分支），断言在写盘前失败恰好保护了并行会话的工作树不被半写文件污染。
- 坑：多个 AI session 并行改同一仓库时，共享的自动生成文件（决策索引、DevNotes、STATUS）会互相踩踏；提交时必须只 stage 自己的文件，并用 `gov-next-decision.sh --create` 原子取号——本次若不核对就已把新决策写成 DEC-015，撞上并行会话正在写的同一号。
- 教训：同一事实出现两个数字不是谁抄错——README 曾用不写口径的「21 项」表述测试总数，指标文档则写「单元测试方法 13」；21 是 Gradle 变体展开的执行数、13 是 `@Test` 方法数，两者都对，缺的只是口径声明。解法不是改数字，而是给全仓数量建立唯一事实源与命名规范（reference §6 术语表 + docstandard 写作规则 + 漂移守卫测试）；口径不落地，改完还会漂，当天读数又变成 26 就是证明。
- 坑：并行会话手工新建决策时直接手写 `# DEC-013` 而没走 `gov-next-decision.sh --create`，合并后同一编号出现两份正文，变更日志 / DevNotes / 决策索引三处互相矛盾；索引生成器又把带 YAML 前置元数据的决策标题解析成 `---`，并残留重复编号行。最终按人类裁决让并发会话改号（013/014 → 017/018）再修生成器重建索引——取号原子化与合并后重建索引，缺任何一件都会留下「同号多义」。
- 坑：R0 只认「最近一次提交刷新了反思」（干净树比 HEAD~1），所以把生成物刷新（STATUS / 决策索引）单独提一次合并，会让 README 反思与上一提交完全相同而直接 FAIL；正确做法是把生成物刷新与正文变更同批提交，或顺手补一条真实经验——本次为此多跑了一轮分支合并。另外注意 `git reset --hard` 会连带清掉并行会话未提交的工程改动，多 session 环境下只能靠分支合并推进，不能靠回退。
- 教训：「断言已加」的提交信息不是断言——`2ad10b3` 的 commit message 与反思都声称补了金丝雀测试，但全历史检索（pickaxe + 测试文件遍历）找不到任何可执行断言，声称纯属文字级。本轮撤回并补齐 4 条真断言后才敢再引用它。教训：凡声称「已加测试」，落盘路径 + 一次失败即红的执行记录缺一不可。
- 坑：同一语义在检测器与修复器里各写一份就会分叉——GOV-TEST 检测器豁免 `tests/` 夹具（注释明言「夹具必须包含被测字符」），pre-commit 的 strip 修复器却没有对应豁免，键帽测试夹具会在提交时被钩子自己吞掉。防线其实是三重凑齐才闭环：夹具改转义构造（对 strip 免疫）、修复器补 `grep -v '^tests/'`、活钩子副本同步。教训：豁免规则必须单一来源，两处手写迟早互食。
- 教训：对抗评审把「条件通过」与「放行」切开是对我的直接纠偏——我一直用「逻辑绿」描述 domain/application 测试通过，终审明确它不构成放行证据：放行只能由最终 SHA 上的纯净构建（G1）+ 真实迁移测试（G3）+ 同 SHA 的 G2/G4 复验共同决定；文档声明、非最终 SHA 的绿、迁移 SQL 存在，三样都不算数。
- 教训：给 UI 立架构约，价值不在原则写得多对，而在每条原则都绑了「机械守卫 + 如实的落地时点」——旧库的病（UiRefresh 全局总线、千行页面文件）有原文可指，v2 的药方若只写「UI 零业务」而不说 ArchUnit 规则哪天上锁（M4 首切片，未落地就标注未落地），那就是新一轮 hope-ware；立约与上锁分离并写明，比假装守卫已存在诚实得多。
- 教训：忠实移植不是抄枚举而是抄行为分界——旧库 8 类记录入口里，weight 实际写入测量表而非健康记录表（Pages.kt:537），差一行取证就会把 weight 错收进健康记录枚举；落库实现镜像云表 UNIQUE(time,type) 后，行为测试立刻显形「同毫秒同类型覆盖」语义。规则移植必带行为测试，就是让这两处分界自己说话。
- 教训：多 session 下「校验红」必须先做归属判定再谈修复——会话收尾时全量校验红 2 项（DEC-023 占位符、索引缺行），取证后确认全是并行会话在途状态、自己的提交在钩子下 0 违规；若当时冲动代修，就会把对方半成品扫进自己的提交。归属证据（谁的文件、谁的测试、哪一步产生）比修复动作先行，是共享仓库里不误伤的前提。
- 坑：写进 README 的教训不等于手部纪律——「同一文件多处编辑不能并行下发」这条明明在案，本轮给 QkIcons.kt 加 import 与 val 时并行发出两条编辑，后者基于旧快照把前者静默覆盖，import 丢失，靠编译器 Unresolved reference 才暴露；已知教训再次命中的根因是它只活在文档里，没有变成操作习惯。修正：同文件的第二条编辑必须等第一条落地后再发，哪怕两条看起来显然独立；跨文件才配并行。
- 教训：接管并行会话的在途批，先取证再动手——本轮开工时工作区躺着另一位会话中断前的首页重构（编译可通过），没有凭任务清单重写，而是先跑全量测试确认 295 项基线、逐文件复审质量、只续写未完成的六个二级页，最后带归属声明（DEC-026）整批入库；「排障靠 IDE、纪律靠记忆」，中断上下文全部从工作区与项目记忆还原，未丢一环。
- 教训：包名迁移的难点不在改名而在「按包名寻址的规则」——ArchUnit 四条规则与负例夹具全部硬编码 `trigger..` 包路径，若只 mv 文件不改规则，守卫会静默失去目标（规则照过、什么都没守）。迁移清单必须先 grep 包名的全部消费者：代码 import、测试规则字符串、文档引用，三类缺一就是又一次「金丝雀虚报」式隐患。
- 坑：python 批量替换里没写 assert 的 replace 就是静默 no-op——R2 给 Room 读映射加快照字段那次，锚点多写了返回类型没匹配上，脚本照样打印成功、文件照常入库（写映射那半确实改了所以审计看不出缺），读路径丢字段的回归一直活到组 B 才被发现。教训：批量改码逐条 assert「命中且唯一」，脚本打印成功不等于每条替换命中；单侧映射必须配往返测试兜底——本次 RoomMappingTest 的回退即红演示就是那块补上的刹车片。

- 坑：「0 违规」不等于「0 警告」——收敛结论落盘时 GOV-SKILL 的 frontmatter WARN 才冒出来，而纪律要求两者都清零；连带发现 R0 的连锁：只要补文档提交不刷反思，合并后全量校验立刻红。终局收尾也要按整链推演，别在最后一步留个带警告的句号。
