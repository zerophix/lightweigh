# 轻刻健康 Android（qk-health-v2）

配合 OKOK 协议蓝牙体脂秤使用的个人健康记录 App。记录体重与体成分数据，
本地优先存储，支持后续云端同步与多成员档案。

## 功能现状（M1）

- 手动记录体重（体脂按 builtin-1 公式计算，无阻抗时记为"未计算"）
- 最近测量列表
- 成员档案字段：性别 / 出生年 / 身高（体脂计算输入）

## 技术架构

Kotlin + Jetpack Compose + Room + Coroutines，四模块分层，依赖只允许向内：

| 模块 | 类型 | 职责 |
|---|---|---|
| domain | 纯 JVM（零 Android 依赖，编译期强制） | 协议解析、体成分算法、测量模型、仓储端口 |
| application | 纯 JVM | 用例编排（RecordMeasurement：取档案 → 算体脂 → 落库） |
| infrastructure | Android 库 | Room 存储、档案存储、（后续：BLE 网关、云同步） |
| app | Android 应用 | Compose 界面（UDF 单向数据流）、组合根、ArchUnit 架构守卫 |

## 快速开始

```bash
./gradlew build        # 构建 + 全部测试 + 架构守卫
```

- 环境：JDK 17+（推荐 Android Studio 自带 JBR 21）、Android SDK 34
- Android Studio：Open 选择本目录，Gradle JDK 选 embedded jbr-21
- 模拟器：使用 arm64 AVD（如 qk_health_avd）；蓝牙称重需真机
- applicationId：com.xcwk.scalehub

## 协议与算法

体脂秤接入是本项目的核心资产：

- 协议：okok-1（GATT 连接式）、okok-broadcast-1（纯广播）、chipsea-cloud-1（芯海云端版），
  帧解析、分包重组、单位换算均在 domain 层，纯 JVM 可测
- 算法：builtin-1（经验公式）、okok-bia-1（设备回归公式），编号定格历史记录，升级不回算
- 算法正确性由黄金向量测试守护（输入输出向量与跨端契约同源，任何一端漂移即测试失败）

## 路线图

- M2：手机号登录与云端同步（CloudBase，离线保存与上云为两个独立承诺）
- M3：蓝牙称重（三协议接入，连接状态机：显式状态枚举 + 串行写队列 + 断连退避重连）
- M4：完整页面（设备绑定 / 趋势图表 / 体测报告 / 健康日志 / 设置 / 档案编辑）
- M5：8 电极分支算法（分部位阻抗 Z14/Z23 合并与专用系数）

### 反思

- 教训：算法必须与设备电极模式严格匹配——早期实现对 8 电极秤套用四电极公式，数值能产出但口径错配，这类静默偏差比崩溃更危险；现已按模式拆分系数并用黄金向量锁定。
- 坑：本地存储带隐式容量上限等于静默丢数据；v2 用 Room 取代旧存储后该问题从结构上消除，但容量与保留语义必须写进契约。
- 教训：批量包名/路径重命名不能依赖 shell 内建替换（转义行为不可控），必须用脚本语言做确定性操作，并在改后做残留复验。
- 教训：拒绝非法数据不等于定义了正确业务规则——每条不变量必须标注来源（契约级/产品级/自设），weight 上限就是产品决策而非厂商契约，混为一谈会让后人误信。
- 坑：测试期望值必须来自独立精算而非印象——单位换算 lb 向量曾手填 69.8，精算为 70.3，当场纠正；这类"期望值笔误"恰是黄金向量机制要防的自身盲区。
- 教训：只存计算结果不存输入的历史无法解释——快照语义必须落到"输入随记录持久化"（schema v2 三列），并用"存档后改档案"测试钉死。
- 教训：空模板事故的根因不是操作失误而是校验盲区——唯一会检查占位符的脚本从未被任何门禁调用，规则写了却不执行等于没写；补规则时又发现按治理笔记的「通用尖括号」思路会误伤合法正文，最终只有用模板 token 白名单并用测试钉住它与模板同步才可靠。
- 坑：去模板化收尾不能只改正文——状态看板的项目名取自 `mkdocs.yml` 的 `site_name`，指标由自动脚本从代码统计生成；不先改源头就重生成，模板身份会立刻「复活」。正确顺序是「先改源头 → 再重生成 → 最后校验」，否则每次收尾都在做无用功。
- 教训：黄金标准（reference/guides 等）不能直接编辑，必须经 `wf-promote.sh` 附一个新 DEC 晋升，正文也不能自带 `## 来源` 行（由晋升脚本写入）；否则来源标注与治理协议对不上，事后审计无法追溯。
- 教训：把「通用模板指标」当成项目指标是一种隐性失真——指标脚本覆盖写入的正文统计的是外壳工具链（Shell/Python 行数），对 Kotlin/Java 工程毫无意义，只在「自定义指标」节追加也消除不了误导。正解是给脚本一个整篇文档覆盖入口，让项目用自己的钩子实时算真指标，脚本保持通用而不硬分叉上游。
- 坑：多个 AI session 并行改同一仓库时，共享的自动生成文件（决策索引、DevNotes、STATUS）会互相踩踏；提交时必须只 stage 自己的文件，并用 `gov-next-decision.sh --create` 原子取号——本次若不核对就已把新决策写成 DEC-015，撞上并行会话正在写的同一号。
- 教训：同一事实出现两个数字不是谁抄错——README 曾用不写口径的「21 项」表述测试总数，指标文档则写「单元测试方法 13」；21 是 Gradle 变体展开的执行数、13 是 `@Test` 方法数，两者都对，缺的只是口径声明。解法不是改数字，而是给全仓数量建立唯一事实源与命名规范（reference §6 术语表 + docstandard 写作规则 + 漂移守卫测试）；口径不落地，改完还会漂，当天读数又变成 26 就是证明。
- 坑：并行会话手工新建决策时直接手写 `# DEC-013` 而没走 `gov-next-decision.sh --create`，合并后同一编号出现两份正文，变更日志 / DevNotes / 决策索引三处互相矛盾；索引生成器又把带 YAML 前置元数据的决策标题解析成 `---`，并残留重复编号行。最终按人类裁决让并发会话改号（013/014 → 017/018）再修生成器重建索引——取号原子化与合并后重建索引，缺任何一件都会留下「同号多义」。
- 坑：R0 只认「最近一次提交刷新了反思」（干净树比 HEAD~1），所以把生成物刷新（STATUS / 决策索引）单独提一次合并，会让 README 反思与上一提交完全相同而直接 FAIL；正确做法是把生成物刷新与正文变更同批提交，或顺手补一条真实经验——本次为此多跑了一轮分支合并。另外注意 `git reset --hard` 会连带清掉并行会话未提交的工程改动，多 session 环境下只能靠分支合并推进，不能靠回退。
- 教训：「断言已加」的提交信息不是断言——`2ad10b3` 的 commit message 与反思都声称补了金丝雀测试，但全历史检索（pickaxe + 测试文件遍历）找不到任何可执行断言，声称纯属文字级。本轮撤回并补齐 4 条真断言后才敢再引用它。教训：凡声称「已加测试」，落盘路径 + 一次失败即红的执行记录缺一不可。
- 坑：同一语义在检测器与修复器里各写一份就会分叉——GOV-TEST 检测器豁免 `tests/` 夹具（注释明言「夹具必须包含被测字符」），pre-commit 的 strip 修复器却没有对应豁免，键帽测试夹具会在提交时被钩子自己吞掉。防线其实是三重凑齐才闭环：夹具改转义构造（对 strip 免疫）、修复器补 `grep -v '^tests/'`、活钩子副本同步。教训：豁免规则必须单一来源，两处手写迟早互食。
- 教训：对抗评审把「条件通过」与「放行」切开是对我的直接纠偏——我一直用「逻辑绿」描述 domain/application 测试通过，终审明确它不构成放行证据：放行只能由最终 SHA 上的纯净构建（G1）+ 真实迁移测试（G3）+ 同 SHA 的 G2/G4 复验共同决定；文档声明、非最终 SHA 的绿、迁移 SQL 存在，三样都不算数。
- 教训：给 UI 立架构约，价值不在原则写得多对，而在每条原则都绑了「机械守卫 + 如实的落地时点」——旧库的病（UiRefresh 全局总线、千行页面文件）有原文可指，v2 的药方若只写「UI 零业务」而不说 ArchUnit 规则哪天上锁（M4 首切片，未落地就标注未落地），那就是新一轮 hope-ware；立约与上锁分离并写明，比假装守卫已存在诚实得多。
- 教训：忠实移植不是抄枚举而是抄行为分界——旧库 8 类记录入口里，weight 实际写入测量表而非健康记录表（Pages.kt:537），差一行取证就会把 weight 错收进健康记录枚举；落库实现镜像云表 UNIQUE(time,type) 后，行为测试立刻显形「同毫秒同类型覆盖」语义。规则移植必带行为测试，就是让这两处分界自己说话。
- 教训：多 session 下「校验红」必须先做归属判定再谈修复——会话收尾时全量校验红 2 项（DEC-023 占位符、索引缺行），取证后确认全是并行会话在途状态、自己的提交在钩子下 0 违规；若当时冲动代修，就会把对方半成品扫进自己的提交。归属证据（谁的文件、谁的测试、哪一步产生）比修复动作先行，是共享仓库里不误伤的前提。
- 教训：包名迁移的难点不在改名而在「按包名寻址的规则」——ArchUnit 四条规则与负例夹具全部硬编码 `trigger..` 包路径，若只 mv 文件不改规则，守卫会静默失去目标（规则照过、什么都没守）。迁移清单必须先 grep 包名的全部消费者：代码 import、测试规则字符串、文档引用，三类缺一就是又一次「金丝雀虚报」式隐患。
